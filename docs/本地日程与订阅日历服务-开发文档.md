## 2. 项目目标

构建一个单用户、轻量、私有的日程管理服务。用户在电脑浏览器中编辑日程；服务将 SQLite 中的日程同步生成标准 iCalendar 文件，并通过 Tailscale Serve 向 iPhone 提供只读订阅地址。用户可在应用中维护参与同步人员的邮箱列表；每次确认保存日程变更并成功生成新版 ICS 后，系统通过邮件向所有启用的同步人员发送该版本中**尚未结束的日程**快照（完整历史由订阅地址提供）。

系统的核心原则如下：

1. SQLite 是日程数据的唯一事实来源。
2. `calendar.ics` 是由数据库派生的发布文件，不允许用户直接编辑。
3. 管理入口只允许本机访问；iPhone 只能访问订阅入口。
4. Docker 端口只绑定回环地址，不向局域网或公网直接开放。
5. Tailscale 负责设备身份、网络访问控制和公网样式 HTTPS 终止。

以上五条在家庭版中依然成立。2026-10-08 的演进（第 18 章）把部署形态从单用户扩展为 3–5 人的家庭共享：新增账号、私人日历、共享日历与成员角色，邮件与订阅地址都改为按账号范围分发，SQLite 仍是唯一事实来源。

2026-10-12 的演进（第 18.11–18.13 节）在此基础上收敛了「地址」与「人」：公开面只有一个基地址
`PUBLIC_BASE_URL`（路径部分即挂载前缀），旧的**无令牌**订阅地址 `/calendar` 与 `/calendar.ics` 取消，
每人一条在账号创建时派生、永不变更的固定订阅地址；成员必须绑定邮箱并通过一次 SMTP 验证码验证，
验证通过后才会收到含自己固定地址的邮件。

## 3. 范围与假设

### 3.1 第一版范围

- 在月、周、日历列表界面中查看日程。
- 新建、编辑、删除普通日程和全天日程。
- 支持标题、时间、时区、地点、说明、链接、提醒和重复规则。
- 数据修改后自动生成最新的 `calendar.ics`。
- iPhone 通过固定 HTTPS 地址订阅只读日历。
- 配置 SMTP 发信账户和参与同步人员邮箱列表。
- 每次用户确认保存日程变更且新版 ICS 生成成功后，自动向启用的同步人员发送邮件，并附上该版本中**尚未结束**的全部日程（不含已结束的事件）。
- 显示 ICS 生成状态、最后生成时间和邮件同步状态。
- 提供 Docker Compose 部署、持久化、健康检查和备份说明。

### 3.2 邮件同步的第一版定义

“邮件同步”在第一版中定义为新版日历文件的出站分发，不包含收取或解析来信：

- 用户在应用设置中新增、启用、停用或移除参与同步人员邮箱地址。
- 一次“同步动作”由用户在新建、编辑或删除日程时点击最终的“保存并同步”触发；输入过程中的自动保存或草稿不触发邮件。
- 数据库保存成功且新版 `calendar.ics` 原子生成成功后，系统为本次导出创建邮件发送任务。
- 系统向当时所有处于启用状态的同步人员分别发送一封邮件，附件是**该版本中尚未结束的事件**（含正在进行与仍在重复的事件），而不是只包含本次修改事件的局部文件。已经结束的事件一律不进附件（包含当天早些时候刚结束的）：邮件是通知，历史留在长期订阅地址里。
- 邮件正文同时说明本次操作类型、事件标题、操作时间和长期订阅地址（**2026-10-12 起**：账号收件人收到的是**他自己**那条固定订阅地址，外部邮箱一条地址都不给，见第 18.6 节），方便有 Tailscale 权限的人员直接订阅。
- 每个“导出版本 + 收件人”只能成功发送一次；失败任务按退避策略自动重试，也允许管理员手动重试。
- 删除事件时，附件为已经排除该事件的新版“尚未结束的日程”快照。
- 修改同步人员列表本身不自动发送邮件；设置页提供“向当前人员发送最新版”按钮，并要求二次确认。

邮件附件是一份日历快照，不等同于持续订阅。不同邮件客户端对重复导入 ICS 的合并行为可能不同，因此邮件主要用于通知和离线获取；需要持续自动更新的人员仍应使用固定订阅地址。**发布文件 `calendar.ics`（订阅源）始终包含全部事件，包括过去的事件**——手机上要看得到历史，而且导出内容必须只取决于数据库状态（`AGENTS.md` 不变量 3）。第一版不实现 IMAP 收件、邮件邀请响应、CalDAV，或 Gmail、Outlook、iCloud 日历账户的双向同步。

### 3.3 第一版不包含

- CalDAV 双向日历服务器。
- 多用户、团队权限或公开注册。
- 手机端管理界面。
- 无 Tailscale 的公网访问。
- 与 Exchange、Google Calendar 或 iCloud Calendar 的完整双向同步。
- 会议室、资源预订、参会状态统计等企业日历功能。

### 3.4 第四轮需求（2026-10-12）：公开地址、固定订阅地址与邮箱验证

本轮的四条需求在家庭版（第 18 章）的基础上收紧了「地址」与「身份」两件事，共同的前提是
**公开面只有一个基地址**：`PUBLIC_BASE_URL`（默认 `https://sisi-laptop.tail921448.ts.net/calendar`）。
它的**路径部分**（`/calendar`）就是整套公开路由的挂载前缀，成员登录、注册、管理界面与每人的
订阅地址都在这一个前缀下；本机管理入口仍是裸路径 `http://localhost:443/admin`。

1. **停止把根域名当订阅地址，正式基地址带 `/calendar` 前缀。** 旧的**无令牌**订阅地址
   `/calendar` 与 `/calendar.ics`（升级前等价于「首位管理员的可见范围」）**取消**，只保留程序
   生成的令牌版地址；`/calendar` 前缀本身对订阅端回 404 纯文本（对浏览器 303 到管理页）。
2. **邀请码生成时直接给出完整邀请链接。** 形如
   `https://sisi-laptop.tail921448.ts.net/calendar/register?code=<邀请码>`，管理员可整条复制给家人，
   对方粘贴即用，不必自己拼域名。
3. **每人的订阅地址在账号创建时自动生成、永远不变。** 地址由服务端密钥派生
   （`HMAC(session_secret, "feed:<账号id>")`），因此界面可以长期显示、验证通过后可以邮件告知，
   而库里仍然只存 `sha256`；界面不提供停用/撤销。
4. **必须绑定邮箱并完成一次 SMTP 验证码验证。** 注册必须填邮箱；验证码 6 位、30 分钟有效、
   最多错 5 次、重发冷却 60 秒；验证通过后才发第二封邮件告知其**固定订阅地址**。验证前成员
   不能使用系统（页面 303 到验证页，`/api` 返回 403），也不能成为邮件收件人；首位管理员豁免。

四条需求的功能条目与验收判据分别见第 18.5、18.11、18.12、18.13 节与第 18.10 节的 F26–F43。

## 4. 技术选型

| 层级 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.13 | 日历、邮件和 Web 生态成熟，镜像体积和维护成本适中 |
| Web 框架 | FastAPI | 同一项目内提供页面、REST API、健康检查和后台任务接口 |
| 页面 | Jinja2 + HTMX | 无需独立 Node 构建链，适合单用户轻量应用 |
| 日历界面 | FullCalendar | 提供成熟的月/周/日视图、拖动和事件编辑能力 |
| 数据库 | SQLite | 单机单用户足够，备份和迁移简单 |
| 数据访问 | SQLAlchemy 2 + Alembic | 明确模型边界并提供可追踪的数据库迁移 |
| ICS | Python `icalendar` 库 | 避免手工处理转义、折行、日期和时区格式 |
| 邮件 | Python 标准库 `email`、`smtplib` | 生成带 ICS 附件（尚未结束的日程快照）的 MIME 邮件并通过 SMTP 发送 |
| 后台任务 | 持久化发送队列 + APScheduler | 执行失败重试、超时恢复与 ICS 修复任务 |
| 部署 | 单应用容器 + Docker Compose | 组件少，便于本地部署、启动和备份 |

SQLite 建议启用 WAL，但只运行一个应用进程。运行时应选用已经修复 WAL-reset 问题的 SQLite 版本；不要为了吞吐量启动多个写进程。若未来改成多用户或高并发，再迁移到 PostgreSQL。

## 5. 总体架构

```text
电脑浏览器
    |
    | http://localhost:443/admin
    v
127.0.0.1:443  --Docker 端口映射-->  FastAPI :8000
                                            |
                       +--------------------+--------------------+
                       |                    |                    |
                    SQLite           calendar.ics             SMTP
                       |              派生文件               发信服务器
                       +--------------------+
                                            ^
                                            |
iPhone 日历 --> Tailscale HTTPS /calendar/<令牌>.ics --+
```

### 5.1 两个入口

管理入口（本机）：

- URL：`http://localhost:443/admin`
- 用途：查看和编辑日程、配置 SMTP 和同步人员、查看同步状态。
- 访问范围：仅 Docker 主机自身。
- 保护方式：Docker 只绑定 `127.0.0.1`，并增加管理员登录与会话校验作为第二层保护。

公开入口（家庭成员，2026-10-12 起统一挂在一个前缀下）：

- 基地址：`https://sisi-laptop.tail921448.ts.net/calendar`（配置项 `PUBLIC_BASE_URL`，路径部分即前缀）
- 用途：成员登录 `/calendar/login`、邀请码注册 `/calendar/register`、邮箱验证 `/calendar/verify-email`、管理界面 `/calendar/admin/...`，以及每人的订阅地址 `/calendar/<令牌>.ics`。
- 访问范围：仅允许通过 Tailscale tailnet 到达。
- Tailscale 只挂载 `/calendar` 一段（外加 DSH 自己的 `/`、`/dsh` 与 Bearer-only 的 `/agent`），**不再挂裸** `/login`、`/logout`、`/register`、`/admin`、`/api`、`/static`。
- 旧的无令牌订阅地址 `/calendar` 与 `/calendar.ics` **不再提供日历**，一律纯文本 404（见第 18.5、18.11 节）。

### 5.2 TLS 边界

容器内部和主机回环地址使用 HTTP。端口号虽然是 443，本机管理地址仍明确写成 `http://localhost:443/admin`。Tailscale Serve 在外层终止 HTTPS，并将 `/calendar` 请求反向代理到 `http://127.0.0.1:443`。

这样不需要在容器内保存私钥，也不会让浏览器面对自签名证书。如果未来强制要求本机也使用 `https://localhost`，应另行增加本地 TLS 代理和受信任证书，不属于第一版。

## 6. 功能需求

### 6.1 日程管理界面

首页默认显示当前月份，并提供月、周、日、列表视图切换。

事件字段：

- 标题，必填，1–200 字符。
- 开始时间和结束时间，必填；结束必须晚于开始。
- 全天事件开关。
- 时区，默认读取应用配置，建议初始值为 `Australia/Brisbane`。设置页以下拉框给出 30 个常用时区
  （北京时间、悉尼时间等，按地区分组并带固定序号）；事件与接口的 `timezone` 字段除 IANA 名外，
  也接受这个序号或中文名，方便不便读取设备时区的调用方（如 iOS 快捷指令）。
- 地点，选填，最多 500 字符。
- 说明，选填，最多 10,000 字符。
- 链接（URL），选填，最多 1,000 字符；导出为 `VEVENT` 的 `URL` 属性。
- 提醒，选填，可多选；每一项是相对事件开始时间的偏移分钟数（`0` = 开始时，正数 = 提前，
  负数 = 延后，绝对值上限 30 天），界面提供常用预设并允许自定义多个值。
  全天事件以开始日期当天 `00:00` 为基准，因此 `1440` 表示前一天零点。
  每条提醒导出为一个 `VALARM`；不选则不导出任何 `VALARM`。
  取值、去重与排序规则见 `docs/static/app-reminders.md`。
- 重复规则，选填；第一版支持不重复、每天、每周、每月、每年和截止日期。

操作要求：

- 新建、编辑、删除必须有明确的成功或失败提示。
- 删除采用软删除，并从 ICS 中立即移除；第一版可不提供回收站界面。
- 拖动事件改变时间后必须弹出确认，不能静默修改。
- 并发编辑使用 `updated_at` 或版本号检查，避免旧页面覆盖新数据。
- 列表提供关键词、日期范围和来源筛选。

### 6.2 ICS 同步

数据库是唯一事实来源。任何经过用户确认的日程新增、修改或删除完成后，执行以下流程：

1. 在数据库事务中保存事件并更新事件版本。
2. 提交成功后，将导出状态设为 `dirty`。
3. 读取当前全部有效事件，生成完整 ICS 内容。
4. 先写入同目录临时文件，刷新并完成后原子替换 `/data/export/calendar.ics`。
5. 计算 SHA-256，更新导出版本、生成时间和 `dirty=false`。
6. 为该导出版本和所有启用的同步人员创建幂等邮件任务。
7. 只有数据库写入和 ICS 生成都成功，界面才显示“日程已同步”；邮件状态单独显示为待发送、已发送、部分失败或失败。

若第 3–5 步失败：

- 数据库中的编辑不能丢失。
- 页面显示“ICS 待修复”及错误摘要。
- 后台任务每分钟重试。
- 订阅入口检测到 `dirty=true` 时先尝试同步生成；如果仍失败，返回最近一个有效文件，并附带告警日志，不能返回半写入文件。
- 应用启动时必须执行一次数据库与 ICS 一致性检查。

### 6.3 订阅响应

**订阅入口只有带令牌的一种**（2026-10-12 起）：

```text
GET|HEAD <公开基地址>/<令牌>.ics       例如 https://<节点>/calendar/sisi_feed_<40位hex>.ics
```

无令牌的 `GET /calendar` 与兼容别名 `GET /calendar.ics` **已取消**：对日历客户端（`Accept` 不含
`text/html`）返回 `404` 纯文本，对浏览器返回 `303` 到管理页，任何情况下都不再输出 ICS。

响应至少包含：

```text
Content-Type: text/calendar; charset=utf-8
Content-Disposition: inline; filename="calendar.ics"
ETag: "<内容哈希>"
Last-Modified: <最后生成时间>
Cache-Control: private, max-age=300, must-revalidate
```

支持 `If-None-Match` 和 `If-Modified-Since`，内容未变化时返回 `304 Not Modified`。令牌无效或已停用返回 `404` 纯文本。订阅地址不做 HTML 重定向，避免 iPhone 保存错误地址。

### 6.4 iCalendar 兼容要求

导出文件遵循 RFC 5545：

- 使用 UTF-8、CRLF 行结束符和规定的内容行折叠。
- 根对象包含 `BEGIN:VCALENDAR`、`VERSION:2.0`、稳定的 `PRODID` 和 `CALSCALE:GREGORIAN`。
- 订阅文件和邮件附件均不设置 `METHOD`，以表明它们是日历快照而不是会议邀请事务。
- 每个事件使用永久稳定的 `UID`，创建后不得变化。
- `DTSTAMP` 使用 UTC。
- 修改事件时递增 `SEQUENCE`，同时更新 `LAST-MODIFIED`。
- 全天事件使用 `VALUE=DATE`，`DTEND` 为不包含在事件内的次日日期。
- 有时间的事件保存 UTC 时间与原始 `TZID`；需要时生成对应 `VTIMEZONE`。
- 正确转义反斜线、逗号、分号和换行。
- 提醒导出为 `VALARM`：`ACTION:DISPLAY`、`DESCRIPTION` 为事件标题、`TRIGGER` 使用
  **相对时长**（如 `-PT15M`、`-P1D`），不使用 `TRIGGER;VALUE=DATE-TIME` 绝对时间。
  相对时长让重复事件与跨时区/夏令时事件由订阅端按各自实例计算，无需逐实例生成提醒。
  子组件顺序与事件提醒列表一致（列表已去重并按从大到小排序），保证内容哈希稳定。
- 链接非空时输出 `URL` 属性。
- 无提醒、无链接的事件导出结果与不启用该功能时**逐字节一致**，避免升级本身触发重发。
- 重复事件使用标准 `RRULE`；第一版暂不提供复杂的单次例外编辑，除非实现 `RECURRENCE-ID`。

### 6.5 邮件同步

邮件设置包括：

- SMTP 主机、端口、STARTTLS/SSL、用户名、密码、发件人名称和地址。
- 参与同步人员邮箱列表；每项包含邮箱地址、显示名称、启用状态、创建时间和最后成功发送时间。
- 自动重试次数与退避间隔，默认最多 5 次：1、5、15、60、180 分钟。
- “测试连接”、“发送测试邮件”和“向当前人员发送最新版”。

安全要求：

- 密码不得写入 SQLite、日志、镜像或版本库。
- 第一版通过 `.env` 或 Docker Secret 注入凭据；设置页只显示是否已配置，不回显密码。
- 日志中的邮箱地址应脱敏显示，邮件正文和附件内容不得记录。
- 连接必须验证服务器证书，禁止默认跳过 TLS 验证。

发送规则：

- 触发顺序固定为：保存数据库 → 生成新版 ICS → 固化导出版本 → 创建发信任务 → 后台发送。
- 每位收件人单独发送，避免在 `To` 或 `Cc` 中泄露其他同步人员的邮箱地址。
- 附件名称固定为 `calendar.ics`，MIME 类型为 `text/calendar; charset=utf-8`，内容必须与该任务记录的不可变快照逐字节一致（该快照是“尚未结束的日程”子集，不一定等于发布文件）。
- 发送任务创建时保存一份不可变的 ICS 快照或其受保护路径，避免重试时错误地附上更晚版本。发布文件与版本快照保持完整，只有**邮件专用快照**按“此刻”过滤。
- 幂等键为 `export_version + recipient_id`，数据库建立唯一约束。
- 邮件主题建议为“日程已更新：{事件标题}”；删除时使用“日程已移除：{事件标题}”。
- 正文包含变更摘要、生成时间、订阅地址和“附件只含尚未结束的日程、完整历史请看订阅地址”的提示。
  **2026-10-12 起**：只有账号收件人（`sync_recipients.user_id` 非空）会收到订阅地址，而且一定是他
  **自己**那条固定地址；外部邮箱（含单用户版升级上来的历史邮箱）正文里一条地址都不给，只提示地址
  在本人账号的「我的设置」里，见第 18.6 节。
- 正文里的“事件时间”按**调用方提交时间所带的偏移量**表述（调用方没带偏移量时按事件时区）；事件的参照时区与订阅日历显示不受影响。
- 一个收件人失败不得阻止其他收件人发送。
- 邮件发送失败不能回滚本地日程或 ICS；界面显示失败人员、原因摘要、重试次数、操作时间、
  发送时间和下次重试时间。
- 当存在连续失败时，后续新版仍创建独立任务；旧任务重试必须继续使用对应旧版附件，不能冒充新版。
- 新增或编辑同步人员时必须提示：该人员通过订阅地址可以看到完整日历（含过去事件）；邮件附件只含尚未结束的日程。**2026-10-12 起**：账号邮箱只能由账号本人在「我的设置」维护，外部收件人接口不得改账号收件人的邮箱或删除它（`409`）。

## 7. 数据模型

### 7.1 `events`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID/Text, PK | 内部主键 |
| `uid` | Text, Unique | 对外 ICS UID，创建后不可更改 |
| `title` | Text | 标题 |
| `description` | Text/Null | 说明 |
| `location` | Text/Null | 地点 |
| `url` | Text/Null | 备注链接，导出为 ICS `URL`（`0004_event_reminders`） |
| `reminders` | Text/Null | 提醒偏移分钟数的 JSON 列表，如 `[1440, 15, 0]`；空为 `NULL`（`0004_event_reminders`） |
| `start_at_utc` | DateTime/Null | 非全天事件 UTC 开始时间 |
| `end_at_utc` | DateTime/Null | 非全天事件 UTC 结束时间 |
| `start_date` | Date/Null | 全天事件开始日期 |
| `end_date_exclusive` | Date/Null | 全天事件不含终止日期 |
| `timezone` | Text | IANA 时区名 |
| `all_day` | Boolean | 是否全天 |
| `rrule` | Text/Null | 标准重复规则 |
| `status` | Text | `confirmed`、`tentative`、`cancelled` |
| `sequence` | Integer | ICS 修改序号 |
| `created_at` | DateTime | 创建时间 |
| `updated_at` | DateTime | 更新时间及乐观锁依据 |
| `deleted_at` | DateTime/Null | 软删除时间 |

### 7.2 `sync_recipients`

- `id`
- `email`
- `display_name`
- `enabled`
- `created_at`
- `updated_at`
- `last_sent_at`

邮箱地址经过规范化后建立唯一约束。同步人员是应用级配置，会收到整个日历，而不是单一事件的参会人。

### 7.3 `mail_deliveries`

- `id`
- `export_version`
- `recipient_id`
- `trigger_event_id`
- `change_type`
- `attachment_hash`
- `snapshot_path`
- `status`：`pending`、`sending`、`sent`、`retry_wait`、`failed`
- `attempt_count`
- `next_attempt_at`
- `error_message`
- `created_at`
- `sent_at`

`export_version + recipient_id` 建立唯一约束。

### 7.4 `calendar_exports`

用于保留邮件任务所需的不可变版本快照：

- `version`
- `content_hash`
- `snapshot_path`
- `size_bytes`
- `created_at`

同一个版本在 `snapshots/` 下有两个文件：`calendar-v{N}.ics`（完整，`snapshot_path` 指向它，哈希即 `content_hash`）与 `calendar-v{N}-upcoming.ics`（仅尚未结束的日程，仅供邮件附件，路径由版本号推导、不单独建列）。邮件任务记录的 `snapshot_path` / `attachment_hash` 指向后者；后者缺失时回退到前者。

当一个版本的全部发送任务均进入最终状态且超过保留期后，后台任务可以清理该版本快照（两个文件一起清理）；当前发布版本不得清理。

### 7.5 `calendar_export_state`

单行表：

- `version`
- `content_hash`
- `generated_at`
- `dirty`
- `last_error`

### 7.6 `app_settings`

保存非敏感配置，例如日历名称、默认时区、默认提醒和邮件重试策略。SMTP 密码不进入此表。

### 7.7 `agent_tokens`

远程 Agent 接入令牌（`migrations/versions/0003_agent_tokens.py`）：

- `id`：UUID 主键
- `label`：给人看的名称，≤100 字符
- `token_hash`：`sha256(明文)`，**唯一约束**；令牌明文不进入此表
- `enabled`：停用后立即失效但保留记录（有索引）
- `created_at` / `updated_at`：naive UTC

令牌明文只在创建成功那一次响应里出现，之后界面只能看到指纹（`token_hash` 前 16 位）。
详见 `docs/static/app-token-store.md`。

### 7.8 第四轮需求新增的列（`0007_email_verification`）

`users` 新增 5 列（全部可空，`batch_alter_table` 兼容 SQLite），迁移同时把**升级前就存在**的邮箱
视为已验证（`email_verified_at = created_at`，否则老成员升级后会被验证页挡住）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `email_verified_at` | DateTime/Null | 验证通过时间；为空即「待验证」 |
| `email_verify_code_hash` | Text/Null | 6 位验证码的 `HMAC(session_secret, "verify:<账号id>:<验证码>")`，**不存明文** |
| `email_verify_expires_at` | DateTime/Null | 验证码失效时间（默认 30 分钟） |
| `email_verify_attempts` | Integer，默认 `0` | 已错误次数；达到 5 次时作废验证码 |
| `email_verify_sent_at` | DateTime/Null | 最近一次发送时间，用于 60 秒重发冷却 |

## 8. 页面与接口

### 8.1 页面

**2026-10-12 起**，表中路径都是**应用内部路径**：本机用裸路径访问，家庭成员用同一个基地址的
路径前缀（默认 `/calendar`）访问，两套入口是同一套逻辑。绝对地址见第 18.11 节。

| 路径 | 用途 |
|---|---|
| `/admin` | 日历主界面 |
| `/admin/events/new` | 新建日程 |
| `/admin/events/{id}` | 查看和编辑日程 |
| `/admin/settings` | 日历、SMTP 和同步人员配置 |
| `/admin/sync` | ICS 与邮件发送状态、错误及重试 |
| `/login` | 登录（本机管理员与家庭成员共用） |
| `/register?code=...` | 邀请码注册（**2026-10-12 起必须填邮箱**） |
| `/verify-email` | 邮箱验证页：输入 6 位验证码、重新发送、改邮箱 |
| `/admin/me` | 我的设置：资料、口令、**我的固定订阅地址** |

**2026-10-12 起**：前缀本身 `<基地址>`（如 `/calendar`）对订阅端返回 `404` 纯文本、对浏览器
`303` 到 `/admin`，不再提供日历。

### 8.2 REST API

| 方法与路径 | 用途 |
|---|---|
| `GET /api/v1/events` | 按日期范围和条件查询事件 |
| `POST /api/v1/events` | 新建事件 |
| `GET /api/v1/events/{id}` | 读取事件 |
| `PATCH /api/v1/events/{id}` | 修改事件 |
| `DELETE /api/v1/events/{id}` | 软删除事件 |
| `GET /api/v1/sync/status` | 查询 ICS 和邮件同步状态 |
| `POST /api/v1/sync/calendar` | 手动重新生成 ICS |
| `POST /api/v1/sync/mail/send-latest` | 确认后向当前启用人员发送最新版 |
| `POST /api/v1/mail-deliveries/{id}/retry` | 重试一次失败的发送任务 |
| `GET /api/v1/sync-recipients` | 查询同步人员 |
| `POST /api/v1/sync-recipients` | 新增同步人员 |
| `PATCH /api/v1/sync-recipients/{id}` | 修改名称或启用状态 |
| `DELETE /api/v1/sync-recipients/{id}` | 移除同步人员 |
| `POST /api/v1/settings/mail/test` | 测试邮件连接 |
| `GET /healthz` | 进程健康检查 |
| `GET /readyz` | 数据库、数据目录和导出状态检查 |

所有修改接口要求登录、CSRF 防护、请求体校验和结构化错误响应。公开订阅接口只有 `GET` 和 `HEAD`，
且路由是 `<基地址>/<令牌>.ics`（见第 6.3、18.5 节）。**2026-10-12 起**：非管理员账号「有邮箱但未验证」
时，所有 `/api` 请求返回 `403` 与错误码 `email_not_verified`（页面则 `303` 到 `/verify-email`）。

`timezone` 字段接受 IANA 名、中文名或设置页常用时区下拉框中的序号（1 基，如 `1` = 北京时间）；
序号表顺序固定，只允许在末尾追加，已发布的编号不得调整。清单可通过
`GET /api/v1/settings` 的 `timezone_choices` 读取。

### 8.3 远程 Agent 接口与接入令牌

`/api/agent` 是可选的可写接口，供本机之外的脚本、LLM Agent 或 iOS 快捷指令新建日程，
只认 `Authorization: Bearer`（不接受 Cookie 会话）。令牌有两个来源，鉴权时**取并集**：

| 来源 | 存放方式 | 管理方式 |
|---|---|---|
| 环境变量 `AGENT_API_TOKEN` | `.env` 明文，可逗号分隔多个 | 改文件后重启容器 |
| 数据库 `agent_tokens` 表 | **只存 `sha256(token)`**，明文仅在创建时返回一次 | 设置页「远程接入令牌」卡片：生成 / 改名 / 停用 / 撤销 |

安全约定：令牌明文不写数据库、不写日志、不回显；列表只展示指纹（哈希前 16 位），
与审计日志中的 `agent:<指纹>` 一一对应。管理操作走登录 + CSRF。
两个来源都没有令牌时整段返回 404 而不是 401，避免暴露接口存在。

## 9. Docker 部署设计

建议目录：

```text
project/
├─ app/
├─ migrations/
├─ static/
├─ templates/
├─ tests/
├─ Dockerfile
├─ compose.yaml
├─ pyproject.toml
├─ uv.lock
├─ .env.example
└─ data/                  # 运行时创建，不进入版本库
   ├─ calendar.db
   └─ export/
      └─ calendar.ics
```

Compose 约束：

```yaml
services:
  calendar:
    build: .
    ports:
      - "127.0.0.1:443:8000"
    volumes:
      - ./data:/data
    env_file:
      - .env
    restart: unless-stopped
```

实现时还应补充：

- 健康检查访问容器内 `http://127.0.0.1:8000/healthz`。
- 使用非 root 用户运行。
- 基础镜像固定到明确版本，依赖使用锁文件固定。
- 日志输出到标准输出，由 Docker 管理轮转。
- `/data` 是唯一需要持久化和备份的应用数据目录。
- 容器停止时等待正在进行的数据库事务和 ICS 原子替换完成。

端口必须写成 `127.0.0.1:443:8000`，不能省略主机 IP。省略后 Docker 通常绑定 `0.0.0.0`，会把管理服务暴露给局域网或其他接口。

## 10. Tailscale Serve 配置

应用部署并验证本机地址后，预期配置命令为：

```powershell
tailscale serve --bg --yes --https=443 --set-path=/calendar http://127.0.0.1:443/calendar
```

该操作应新增 `/calendar` 路由，而不是重置全部 Serve 配置。当前设备已有其他 Serve 路由时，部署人员必须先执行 `tailscale serve status` 并保存配置快照，避免误删既有入口。

期望状态：

```text
https://sisi-laptop.tail921448.ts.net/calendar
|-- proxy http://127.0.0.1:443/calendar
```

Tailscale ACL 应只允许指定用户或设备访问该节点的 Serve 服务。**2026-10-12 起**成员面只挂 `/calendar`
一段（外加 DSH 自己的 `/`、`/dsh` 与 Bearer-only 的 `/agent`），裸 `/login`、`/logout`、`/register`、
`/admin`、`/api`、`/static` 都不再挂出，确认这些 tailnet 地址不可访问：

- `https://sisi-laptop.tail921448.ts.net/admin`
- `https://sisi-laptop.tail921448.ts.net/api/v1/events`

> **2026-10-11 更新（真机实测口径，2026-10-12 已按第四轮需求收敛）**：目标地址必须与挂载路径逐字一致，
> 即 `--set-path=/calendar http://127.0.0.1:443/calendar`；写成 `http://127.0.0.1:443` 会让 `/calendar/admin`
> 以 `/admin` 命中管理首页。**当时**为了让家人能自助注册/登录，除 `/calendar` 外还按精确路径挂过
> `/login`、`/logout`、`/register`、`/admin`、`/api`、`/static`，权限边界靠账号 + 角色判定。
> 从 2026-10-12 起这些裸挂载**全部撤掉**：公开面已经统一在 `/calendar` 前缀下注册（`/calendar/login`、
> `/calendar/register`、`/calendar/admin/...`），家人不再需要裸路径；本机仍用 `http://localhost:443/admin`。
> 完整命令、路径映射表与检查清单见《部署与运维》第 3 节。

## 11. 安全要求

- Docker 端口仅绑定 IPv4 回环地址；如启用 IPv6，需要单独确认 `::1` 行为。
- 管理员密码首次启动时生成或从环境变量注入，使用 Argon2id 哈希。
- 会话 Cookie 使用 `HttpOnly`、`SameSite=Strict`；本机 HTTP 环境不能强制 `Secure`，因此会话仅用于回环地址。
- 所有修改请求进行 CSRF 校验。
- 页面输出默认 HTML 转义；说明字段不渲染未经清理的 HTML。
- 对登录、邮件测试、手动群发和失败重试进行速率限制。
- Tailscale 身份头只能在确知请求来自 Tailscale Serve 时使用，不能信任客户端自行提交的同名头。
- 不在日志中输出密码、会话、完整邮件内容或 ICS 私密正文。
- **2026-10-12 起**：邮箱验证码与固定订阅地址明文**只允许出现在邮件正文**里；数据库只存验证码的
  HMAC 与订阅令牌的 `sha256`，日志与审计 `detail` 里一律不得出现验证码、邀请码或地址明文。
- **2026-10-12 起**：非管理员账号「有邮箱但未验证」时不能使用系统（页面 303 到验证页、`/api` 403
  `email_not_verified`），也不能成为邮件收件人；首位管理员豁免，避免本机救急被自己的邮箱锁在门外。
- 订阅内容包含私人日程；禁止改用 Tailscale Funnel，除非用户明确接受公开互联网风险并增加独立鉴权。

## 12. 备份与恢复

备份对象：

- `/data/calendar.db`
- SQLite WAL 模式下同时存在的 `calendar.db-wal` 和 `calendar.db-shm`，或使用 SQLite 在线备份 API 生成一致快照。
- `.env` 中的 SMTP 配置应单独安全备份，不能和普通数据压缩包混放。

推荐每天自动生成一份 SQLite 在线备份，保留最近 7–30 天。`calendar.ics` 无需作为关键备份，因为可以从数据库重新生成，但可保留用于故障诊断。

恢复流程：停止容器、恢复一致的数据库快照、启动容器、执行迁移、强制重新生成 ICS、检查 `/readyz`，最后在 iPhone 上验证订阅。

## 14. 验收标准

1. `docker compose up -d` 后服务自动启动，主机重启后可恢复。
2. 局域网其他设备无法直接访问主机 443 端口。
3. 本机可以通过 `http://localhost:443/admin` 登录并完成事件增删改查。
4. 每次修改后 1 秒内完成 ICS 生成，界面显示最新生成时间。
5. `calendar.ics`（内部并集产物，不对外暴露）通过标准解析器校验，中文、全天、时区和重复事件正确。
6. 订阅地址 `<基地址>/<令牌>.ics`（如 `https://sisi-laptop.tail921448.ts.net/calendar/<令牌>.ics`）返回 `200`、正确 MIME 类型和有效 ICS。
7. 内容未变化的条件请求返回 `304`。
8. iPhone 能成功订阅并在系统日历中显示事件。
9. **（2026-10-12 起最终口径）**裸 `/admin`、`/api/v1/events` 等路径**不再通过 Tailscale 暴露**：Serve 只挂 `/calendar` 一段，成员面已全部在 `/calendar/...` 下（第 18.11 节）。本机管理入口 `http://localhost:443/admin` 不受影响；权限边界仍是账号 + 角色。
   - 2026-10-11 至 2026-10-12 之间曾**故意**把裸 `/login`、`/register`、`/admin`、`/api`、`/static` 也挂到 tailnet，靠角色判定兜底；那段口径已被本轮取代。
   - 2026-10-12 起的「订阅命名空间没被污染」判据是：`/calendar` 本身对订阅端 `404` 纯文本、`/calendar/login` 与 `/calendar/register` 返回登录/注册页（第 18.10 节 F26–F29）。
10. 每次“保存并同步”成功生成 ICS 后，所有启用的同步人员各收到一封邮件，**附件取自该任务的不可变快照，其 SHA-256 与任务记录的 `attachment_hash` 一致**；该快照只含该版本中**尚未结束**的日程（已经结束的一律排除），而发布文件 `calendar.ics` 仍含全部事件。
11. 同一导出版本不会对同一人员成功发送两次；部分失败不影响其他人员，并可自动或手动重试。
12. 邮件或 ICS 生成失败时有可见状态和可重试操作，不会损坏数据库或现有 ICS。
13. 备份恢复后事件数量、UID、序列及订阅内容与备份时一致。

以下条目自 2026-10-08「家庭多人共享日历」演进起生效，逐条对应第 18 章的需求；完整表格见第 18.10 节。

14. `alembic upgrade head` 只做结构变更；首次启动由 `ensure_family_setup` 幂等补齐首位管理员、他的私人日历、家庭共享日历、成员关系与账号收件人，`calendar_id` 为空的历史事件全部归入首位管理员的私人日历；重复启动不产生任何副作用。
15. 私人日历只有归属账号可读可写：其他成员与管理员按 id 读取返回 `404`、写入返回 `403`，事件在列表中根本不出现。
16. 共享日历全员可见可订阅，写入仅限 `owner` 与管理员提升的 `editor`；新成员默认 `viewer`；共享日历的创建与成员角色调整只有管理员能做。
17. 邀请码可设使用次数与有效期：有效邀请码能完成 `/register?code=...` 注册并自动登录，次数用尽后不可再注册，停用与过期各有明确提示；注册接口超过每 10 分钟 5 次返回 `429`。
18. 管理员重置口令时生成一次性临时口令，明文只在响应里显示一次；对方首次登录被要求先修改口令。
19. 管理员不能停用自己、不能删除自己、不能取消自己的管理员角色，也不能删除最后一个管理员（均返回 `409`）。
20. 每个账号在**创建时**就得到一条**固定**订阅地址 `<基地址>/<令牌>.ics`（令牌 = `sisi_feed_` + `HMAC(session_secret, "feed:<账号id>")` 前 40 位十六进制），其内容恰为该账号可见日历（私人 + 家庭共享）的合并结果；地址永不变更、界面可以长期显示，但不提供停用与撤销（`409`）。另外仍可在「我的设置」生成一条随机、**只显示一次明文**的临时地址，临时地址撤销后立刻 `404`。
21. 家庭订阅地址（`user_id` 为空的令牌）只导出家庭共享日历；**旧地址 `/calendar` 与 `/calendar.ics` 已取消**：对日历客户端返回 `404` 纯文本、对浏览器 `303` 到管理页，任何订阅地址都不会退化成全库并集，也不会再退回「首位管理员的可见范围」。
22. 订阅令牌与邀请码的明文都只出现在创建成功那一次响应里，库中只有 `sha256`，列表与页面只显示指纹。**例外**是账号的固定地址：它由服务端密钥派生，可以随时重新显示，但库里同样只有 `sha256`，日志与审计里不得出现明文。
23. 每次发布：账号收件人收到自己可见日历里尚未结束的日程，外部邮箱只收到家庭共享日历（**例外**：单用户版升级上来的历史外部邮箱沿用被绑定账号的可见范围，见第 18.6 节）；任何人的私人日程都不会进入别人的邮件；附件哈希与任务记录的 `attachment_hash` 一致。
24. 邮件正文里**没有任何并集地址**：账号收件人收到的是**他自己**那条固定订阅地址，外部邮箱（含历史邮箱）一条地址都不给，只提示地址在各自账号的「我的设置」里；旧 `SUBSCRIPTION_URL` 已彻底取消。
25. 邮件附件的缺省查询起点按应用默认时区的**当地今天**计算：在 UTC+10 这类时区当地刚过午夜时，附件不包含昨天的全天事件。
26. 任何成员的改动都会推进全局 `export_version`；同一 `(export_version, recipient_id)` 不会成功发送两次，重试仍使用该任务记录的不可变快照。

以下四条自 2026-10-12「公开地址与邮箱验证」演进起生效，逐条对应第 18.11–18.13 节的新 F 条目。

27. 公开面只有一个基地址 `PUBLIC_BASE_URL`（默认 `https://sisi-laptop.tail921448.ts.net/calendar`）：成员登录、注册、邮箱验证与管理界面都在它的**路径前缀**下（`/calendar/login` 等），本机仍可用裸路径 `http://localhost:443/admin`；前缀必须与 Tailscale Serve 的挂载路径逐字一致，且不改写请求路径（不剥离前缀）。
28. 邀请码创建成功后，页面直接给出**含基地址的完整邀请链接** `https://…/calendar/register?code=<邀请码>`，管理员复制即可用；列表里只保留 `…/register?code=` 这个形状提示。
29. 成员必须用邮箱注册并完成一次 SMTP 验证码验证：注册必须填邮箱；验证码 6 位、30 分钟有效、最多错 5 次（第 5 次作废）、重发冷却 60 秒；未验证的非管理员成员页面 `303` 到 `/verify-email`、`/api` 返回 `403 email_not_verified`，且不会成为邮件收件人；首位管理员豁免；改邮箱会打回待验证并重发新码；验证码绝不进日志、审计或数据库明文。
30. 验证通过后系统补发一封「你的固定订阅地址」邮件；邮件正文里的地址是按账号派生出来的那条固定地址，服务端可随时重算，因此不需要保存明文。

## 16. 开发前待确认事项

以下问题不会阻碍核心日历开发，但在邮件模块开始前必须确认：

1. 使用哪家发信邮箱及其认证方式：应用专用密码还是 OAuth 2.0？
2. 是否接受每次确认保存都立即发送邮件，还是需要在短时间连续修改时合并为一封？本文默认每次确认保存立即发送。
3. 同步人员是否都应收到完整日历，还是未来需要按人员筛选可见事件？本文默认所有启用人员收到相同的日历；**邮件附件已确定只含尚未结束的日程**（2026-10-06 决定），完整历史通过订阅地址提供。若要按人员筛选，仍需新增配置。
4. 是否需要多个独立订阅日历，还是一个合并日历即可？
5. 是否需要复杂重复事件的“只修改本次”和“修改之后所有事件”？
6. 管理界面是否只允许本机使用，还是未来也需要通过 Tailscale 远程编辑？

本文其他默认答案为：应用专用密码；单一合并日历；第一版不处理复杂重复例外；管理界面仅限本机。

2026-10-08 的「家庭多人共享日历」演进（第 18 章）已就地解决其中两项：第 3 项的“按人员筛选可见事件”已实现为**按收件人范围分发附件**（账号收件人只收到自己可见的日历，外部邮箱只收到家庭共享日历，见第 18.6 节）；第 4 项的“多个独立订阅日历”已实现为**每人一条按账号范围的固定订阅地址加一条家庭共享订阅地址**（见第 18.5、18.13 节）。第 1、2、5、6 项及“管理界面仅限本机”的结论不变。

2026-10-12 的「公开地址与邮箱验证」演进（第 18.11–18.13 节）没有改变上面任何一条结论，只是把它们落到一个基地址上：
订阅地址从“可临时生成”收紧为“账号创建时派生、永不变更”，并给成员加了邮箱验证这道身份闸门。

## 18. 家庭多人共享日历（2026-10 需求演进）

本章是第 3.1 节「第一版范围」的一次正式演进：服务从单用户私有日历扩展为 3–5 人的家庭共享日历，每人一条**只有本人可见**的私人日历，外加一条全家共享的日历。第 1–17 章的需求、架构、部署方式与不变量继续有效，本章只描述新增与变更的部分，并在第 18.10 节给出家庭版的验收标准、第 18.14 节给出测试证据。

本章按两轮演进组织：

- **2026-10-08（18.1–18.10）**：家庭版本体——账号/私人日历/共享日历/成员/邀请码/订阅令牌、隐私优先的权限、按收件人范围分发的邮件、升级引导与附件时间窗口修复。
- **2026-10-12（18.11–18.13）**：「公开地址与邮箱验证」——公开面收敛到唯一基地址 `PUBLIC_BASE_URL`、取消无令牌旧订阅地址、邀请链接直接给出完整地址、每人一条永不变更的固定订阅地址、成员必须通过邮箱验证码验证后才会收到固定地址邮件。

实现位置：迁移 `migrations/versions/0005_family_accounts.py`（结构与数据回填引导）、`migrations/versions/0006_recipient_scope.py`（收件人的身份与范围分离，见第 18.2.7 节）与 `migrations/versions/0007_email_verification.py`（邮箱验证列与回填，见第 18.2.8 节），账号与权限判定 `app/accounts.py`，邀请码 `app/invites.py`，订阅令牌 `app/feed_tokens.py`，邮箱验证 `app/email_verify.py`，公开面地址与前缀 `app/urls.py`，升级引导 `app/bootstrap.py`。本章描述的全部行为均已实现并通过测试（见第 18.14 节）。

### 18.1 演进目标与保持不变的不变量

演进目标：

1. 每位家庭成员用自己的账号登录，私人日程对其他成员（**包括管理员**）不可见。
2. 家庭共享日历全员可见；默认只有管理员能改，可逐个把成员提升为可编辑。
3. 每个账号有独立的订阅地址，内容只含他自己可见的日历，一人的地址泄露不影响其他人。**（2026-10-12 起）**这条地址在账号创建时由服务端密钥派生、永不变更，见第 18.13 节。
4. 邮件按收件人的可见范围分发，私人日程不会进入别人的邮件。
5. 升级不丢数据：原有日程与既有收件人的收信范围保持不变。**（2026-10-12 起）**升级前的无令牌旧订阅地址 `/calendar`、`/calendar.ics` 已取消，不再由首位管理员代表，见第 18.5 节。

以下不变量在家庭版中**没有放松**（与 `AGENTS.md` 一致）：

- 时间一律以 naive UTC 落库；输入带偏移量按偏移解释，不带偏移量按事件的 IANA 时区解释，展示与 ICS 生成时再还原。
- `UID` 创建后永不变更；修改才递增 `SEQUENCE`；无实际变化不递增、不产生新版本。
- 导出内容只取决于数据库状态，不取决于导出时刻（`DTSTAMP` 取事件自身的修订时间）。
- 发布文件只做原子替换：写同目录临时文件、`fsync`、`os.replace`。
- 导出失败不丢数据；订阅端继续返回最近一个有效文件。
- 邮件任务幂等键仍为 `(export_version, recipient_id)`，附件永远取自任务记录的不可变快照。
- SMTP 口令只来自环境变量，不写数据库、不写日志、不回显；日志中的邮箱一律脱敏。
- 全天事件的 `end_date_exclusive` 不含在事件内；`DTEND` 是同义的不含边界日期。
- 订阅路由只有 `GET`/`HEAD`，且无需登录即可访问；**2026-10-12 起**唯一形状是 `<基地址>/<令牌>.ics`，无令牌的 `/calendar` 与 `/calendar.ics` 一律纯文本 `404`。

### 18.2 数据模型（迁移 `migrations/versions/0005_family_accounts.py` + `0006_recipient_scope.py`）

该迁移只做结构变更，不动任何既有数据。所有新列可空，因此升级本身不会让既有数据失效；在启动引导执行之前，事件暂时没有归属日历。

#### 18.2.1 `users`（账号）

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `username` | 唯一登录名；小写字母、数字、点、下划线和连字符，以字母或数字开头，≤64 |
| `display_name` | 显示名，可空，≤100 |
| `email` | 可选且唯一，≤320；**这就是「账号收件人」地址**。**2026-10-12 起新注册必须填邮箱**（升级上来的老账号可以暂时没有） |
| `color` | 该成员日历的默认颜色 |
| `timezone` | 可空；为空表示跟随应用默认时区 |
| `role` | `admin`（家长账号）或 `member` |
| `enabled` | 停用后不能登录，也不再出现在导出与邮件目标里 |
| `must_change_password` | 为真时首次登录强制修改口令 |
| `password_hash` | Argon2id 哈希 |
| `last_login_at` | 最近一次登录时间 |
| `email_verified_at` | 验证通过时间；为空 = 待验证（`0007_email_verification`，见第 18.2.8 节） |
| `email_verify_code_hash` | 验证码的 HMAC，**不存明文**（`0007_email_verification`） |
| `email_verify_expires_at` | 验证码失效时间，默认 30 分钟（`0007_email_verification`） |
| `email_verify_attempts` | 已错误次数，默认 `0`；达到 5 次时验证码作废（`0007_email_verification`） |
| `email_verify_sent_at` | 最近一次发送时间，用于 60 秒重发冷却（`0007_email_verification`） |

用户名唯一索引 `ix_users_username`，邮箱与启用状态各自建索引。

#### 18.2.2 `calendars`（日历）

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `kind` | `personal`（私人日历）或 `shared`（共享日历） |
| `owner_user_id` | 私人日历 = 归属账号；共享日历为 `NULL` |
| `name` | 日历名称，≤100；私人日历默认取「{账号}的日历」 |
| `color` / `sort_order` | 展示用颜色与排序 |

约束：`kind IN ('personal','shared')`；`owner_user_id` 外键指向 `users.id`，`ON DELETE CASCADE`。

#### 18.2.3 `calendar_members`（成员关系）

`(calendar_id, user_id)` 唯一（`uq_calendar_members_pair`），`role` ∈ `owner` / `editor` / `viewer`。只用于共享日历；私人日历不建成员行，归属即 `owner`。

#### 18.2.4 `invite_codes`（邀请码）

- `code_hash`：`sha256(明文)`，**唯一约束**；明文不落库。
- `label`：给人看的名称，≤100。
- `max_uses`：可用次数，默认 `1`，上限 `20`；`used_count` 记录已用次数。
- `enabled`：停用后不可再注册；次数用尽时自动置为 `false`。
- `expires_at`：可空的有效期（naive UTC）。
- `created_by_user_id`：创建者。

#### 18.2.5 `feed_tokens`（订阅令牌）

- `token_hash`：`sha256(明文)`，**唯一约束**；明文不落库。
- `user_id`：有值 = 该账号的可见范围；`NULL` = **家庭共享范围**。
- `label`、`enabled`、`last_used_at`（最近一次被订阅端拉取的时间）。

**2026-10-12 起**，`user_id` 非空的令牌分两类（同一张表、同一套解析逻辑）：

| 类型 | 来源 | `label` | 界面行为 |
|---|---|---|---|
| **账号固定地址** | 由服务端密钥派生，账号创建（含引导回填）时幂等登记 | `账号订阅地址(固定)` | 长期显示、可随时重发，**不能停用/撤销**（`409`） |
| 临时地址 | 账号在「我的设置」里随机生成，明文只显示一次 | 用户自填 | 可单独停用/撤销，撤销后立刻 `404` |

固定地址的明文只由 `HMAC(session_secret, "feed:<账号id>")` 派生，库里仍然只有 `sha256`；详见第 18.13 节。

#### 18.2.6 既有表新增列

`events`：

| 字段 | 说明 |
|---|---|
| `calendar_id` | 外键 `calendars.id`，`ON DELETE SET NULL`，带索引；每个事件必须属于一个日历 |
| `created_by_user_id` | 创建人，可空 |

新增联合索引 `ix_events_calendar_start`（`calendar_id`、`deleted_at`、`start_at_utc`），用于按日历取时间范围。

其余两处：

- `sync_recipients` 新增 `user_id`（`NULL` = 外部邮箱；非空 = 账号收件人），带索引；`0006_recipient_scope` 再加一列 `scope_user_id`（收信范围，带索引），语义见第 18.2.7 节。
- `agent_tokens` 新增 `user_id`（令牌归属账号）与 `calendar_id`（该令牌的默认落库日历）。

权限全部由日历推导，事件本身不单独授权。

#### 18.2.7 迁移 `0006_recipient_scope`：收件人的身份与范围分离

背景是真机升级暴露的缺陷：`0005` 之后的启动引导把**每一个**历史外部收件人都写成
`sync_recipients.user_id = 首位管理员`，同一个账号名下于是出现多行；而 `user_id` 在代码里是
「账号收件人」的**身份标记**（每个账号最多一行），第二次启动时取「唯一一行」的逻辑抛
`MultipleResultsFound`，容器进入重启循环。

该迁移把两件事拆成两列：

| 列 | 语义 |
|---|---|
| `user_id` | **身份**。非空 = 这行是该账号的账号收件人（由 `users.email` 派生，每账号一行）；`NULL` = 外部邮箱 |
| `scope_user_id` | **范围**。发给该邮箱的附件按哪个账号的可见日历裁剪；`NULL` = 家庭共享日历 |

数据步骤：账号收件人（原本 `user_id` 非空）的 `scope_user_id = user_id`；随后修复已有的重复绑定
——同一个 `user_id` 下若有多行，只保留邮箱与该账号 `users.email` 一致的那一行作为账号收件人，
其余行保留原有收信范围（`scope_user_id = 该账号`）但把 `user_id` 置空，于是它们变回
「沿用某账号范围的外部邮箱」，行为与升级前一致；账号本身没有邮箱时该账号名下不应有账号收件人，
全部行同样降级。

取值统一由 `app/accounts.py::recipient_scope_user_id()` 解释，顺序是
`scope_user_id or user_id or None`。

#### 18.2.8 迁移 `0007_email_verification`：邮箱验证列与回填

纯结构变更加一次数据回填，详见第 7.8 节：

1. `users` 新增 5 列：`email_verified_at`、`email_verify_code_hash`、`email_verify_expires_at`、
   `email_verify_attempts`（默认 `0`）、`email_verify_sent_at`；
2. **回填**：升级前就存在的邮箱一律视为已验证
   （`UPDATE users SET email_verified_at = created_at WHERE email IS NOT NULL AND TRIM(email) <> ''`）。
   真机上这些邮箱都是本人提供并一直在收信，不回填会让老成员升级后立刻被挡在验证页外。
   新注册的账号走注册流程，`email_verified_at` 保持为空。

降级只删列。**注意**：迁移刻意不做「未验证就不发信」的数据清理——那由
`app/accounts.py::sync_user_recipient()` 在运行期按「有邮箱且已验证」判定。

### 18.3 权限模型（隐私第一）

| 日历 | 谁可见 | 谁可写 |
|---|---|---|
| 私人日历（`kind='personal'`） | 只有归属账号 | 只有归属账号 |
| 共享日历（`kind='shared'`） | 全体成员（可订阅） | `owner` 与 `editor` |

判定集中在 `app/accounts.py` 的 `CalendarAccess`，路由与导出都必须经过它，不允许各自拼 SQL 判断权限：

- 所有读接口经 `CalendarAccess.viewable_ids()` / `can_view()` 过滤，越界事件在列表里根本不出现；按 id 读取越界事件返回 `404`。
- 所有写接口经 `can_write()` 判定；对可见但只读的日历写入返回 `403`。只有管理员能创建共享日历、调整成员角色。
- **私人日历对管理员同样封闭**：管理员既不能读别人的私人日历（读 `404`），也不能写（写 `403`）。管理员的职责是账号、邀请码与全局设置，不是查看别人的私人日程。
- 共享日历的新成员默认 `viewer`（看得到、改不了）；把某个成员提升为 `editor` 就等于允许他改这条共享日历。
- 新建事件未指定日历时，默认落在自己的私人日历；没有可写日历时返回 `409`。

管理员额外拥有：成员管理（停用/启用、重置口令、改角色、删除）、邀请码管理、应用设置、同步状态与手动发信、外部收件人管理。成员访问 `/admin/members`、`/admin/settings`、`/admin/sync` 以及 `/api/v1/settings`、`/api/v1/sync/*`、`/api/v1/sync-recipients` 返回 `403`；成员可用的写操作只有自己的资料、口令、订阅令牌，以及自己可写日历里的事件。

管理员自身受以下保护：不能停用自己、不能删除自己、不能取消自己的管理员角色；也不能删除最后一个管理员。以上情况均返回 `409`。

### 18.4 账号、注册与口令

- 成员用邀请码自助注册（**2026-10-12 起地址是完整链接** `<基地址>/register?code=...`，如
  `https://sisi-laptop.tail921448.ts.net/calendar/register?code=...`）：邀请码可设使用次数（默认 1，上限 20）与有效期；不可用原因区分「邀请码无效」「使用次数已用完」「已被停用」「已过期」，其中先判次数再判停用，因为用尽的邀请码会被自动停用，提示「次数已用完」更有指导意义。注册成功后自动登录。
- **2026-10-12 起注册必须填邮箱**：缺邮箱返回 `422` 与提示「请填写邮箱:注册后需要用它接收验证码和你的固定订阅地址」；邮箱通过校验后立刻发一封 6 位验证码邮件，账号进入待验证状态（见第 18.12 节）。
- 邀请码明文只在创建成功那一次响应里显示，库里只存 `sha256`；用尽后立刻失效，管理员也可随时停用或删除。
- **2026-10-12 起，邀请码创建成功后页面同时给出可直接复制的完整邀请链接**
  （`app/urls.py::invite_url()` = `PUBLIC_BASE_URL` + `/register?code=<明文>`）；
  邀请码列表里只保留 `…/register?code=` 这个形状提示，明文不再回显。
- 注册接口按来源地址限流：**每 10 分钟 5 次**，超出返回 `429` 并带 `Retry-After`，避免有人拿一枚有效邀请码去暴力猜用户名。
- 管理员在成员页重置口令时，系统生成一次性临时口令（`secrets.token_urlsafe(9)`），明文只在响应里显示一次并提示立即转达；对方首次登录后跳转 `/admin/me?notice=请先修改初始口令`，改完口令才清除 `must_change_password`。
- 停用账号后：无法登录、该账号的 Agent 令牌失效、不再出现在导出目标与邮件目标里，以后生成的订阅文件与邮件都不再包含他；账号可以重新启用，历史数据保留。
- 删除账号会连带删除他的私人日历（含其中的私人日程）、订阅令牌与账号收件人；共享日历里的历史事件保留，只把创建人字段置空，避免删人就把家庭日程抹掉。
- 账号邮箱只在「我的设置」维护：它是账号收件人的唯一来源，清空邮箱即删除对应收件人记录（停止收信）；外部收件人接口拒绝对账号行改邮箱或删除（返回 `409`）。**2026-10-12 起改邮箱会把账号打回待验证并立刻重发验证码**（见第 18.12 节）。

### 18.5 订阅地址（ICS）

**2026-10-12 起：根域名不再当订阅地址，旧的无令牌地址取消。** 唯一形状的订阅地址是
`<公开基地址>/<令牌>.ics`；每人在<b>账号创建时</b>自动得到一条**固定**地址，另有可选的临时地址。

| 地址 | 内容范围 | 说明 |
|---|---|---|
| `<基地址>/<账号固定令牌>.ics` | 该账号可见日历（私人 + 家庭共享）的合并结果 | **账号创建时自动生成、永不变更**；界面长期显示，验证通过后邮件告知，不能停用/撤销（见第 18.13 节） |
| `<基地址>/<临时令牌>.ics` | 同上 | 账号在「我的设置 → 我的订阅地址」随机生成的额外地址，明文只显示一次，可单独停用/撤销 |
| `<基地址>/<family-token>.ics` | 只有家庭共享日历 | 「家庭订阅地址」，即 `user_id` 为空的令牌，适合公用设备或没有账号的外部订阅者 |
| `<基地址>`（前缀本身，旧 `/calendar`） | **不再提供日历** | 对日历客户端 `404` 纯文本、对浏览器 `303` 到 `/admin`；旧 `/calendar.ics` 同样 `404` |

- 固定地址的明文由服务端密钥派生（`sisi_feed_` + `HMAC(session_secret, "feed:<账号id>")[:40]`），
  因此可以随时重新显示、重新发信；库里**仍然只存 `sha256`**（明文不进日志与审计）。随机临时地址的明文
  只在创建成功那一次响应里显示，列表与页面只展示指纹。
- 临时令牌可单独停用或撤销，撤销后该地址**立刻** `404`，因此「换手机」或「链接外泄」只需要再建一枚，不影响其他家庭成员。**固定地址不提供停用/撤销入口**（`409`）：订阅端长期填着它，误操作会让全家人的手机一起断更；要换地址只能轮换服务端密钥（代价见第 18.11 节）。
- 响应仍是 `Content-Type: text/calendar; charset=utf-8`，带 `ETag`、`Last-Modified`、`Cache-Control: private, max-age=..., must-revalidate`，条件请求返回 `304`；令牌无效或停用返回 `404` 纯文本；不做 HTML 重定向，避免 iPhone 把错误页存成日历地址。
- 订阅文件按目标落盘且互不合并：账号目标 `export/feeds/user-<账号id>.ics`，家庭目标 `export/feeds/family.ics`。任何订阅地址都**不会**退化成全库并集，也**不会**再退回「首位管理员的可见范围」。
- 版本号与内容哈希仍由全库**并集**（`export/calendar.ics`）决定：它只是内部一致性产物（版本、`content_hash`、一致性检查用），**不再作为对外订阅地址**；任何成员的改动都会推进全局版本，因此所有订阅端都会拿到新内容。
- 导出目标只包含**启用**账号加家庭目标；停用账号从导出与邮件目标里消失。

### 18.6 邮件收件人与范围

收件人分两类，附件范围按收件人区分：

| 类型 | 来源 | 附件范围 |
|---|---|---|
| 账号收件人 | 账号邮箱（`users.email`），在「我的设置」维护，自动同步成一条收件人记录（`user_id` 非空） | 该账号可见日历里**尚未结束**的日程 |
| 历史绑定的外部邮箱 | 单用户版升级上来的外部收件人：`user_id` 为空、`scope_user_id` 指向首位管理员 | **被绑定账号（首位管理员）的可见范围**里尚未结束的日程——与升级前完全等价 |
| 外部收件人 | 管理员在设置页或 `/api/v1/sync-recipients` 添加的邮箱 | **只有家庭共享日历**里尚未结束的日程 |

**2026-10-12 起，账号收件人必须先验证邮箱**：`sync_user_recipient()` 只认「有邮箱**且**已验证」的账号，
所以待验证账号（以及管理员自己未验证时）不会产生收件人记录，也不会收到任何邮件。

- 每次发布：账号收件人收到自己可见日历的附件，普通外部邮箱只收到家庭共享日历范围（单用户版升级上来的历史邮箱沿用被绑定账号的范围，见上表第二行）；**任何人的私人日程都不会进入别人的邮件**。没有邮箱的账号不产生收件人记录，清空邮箱即停止收信。
- 「历史外部邮箱沿用被绑定账号的可见范围」正是升级等价性的一部分：单用户版时它收到的是当时那份完整日历，升级后首位管理员的可见范围就是同一批日程，所以它的收信范围不变（见第 18.7 节）。这三类范围由 `recipient_scope_user_id()` 统一解释，收件人页面的「范围」列也据此显示「本人可见日历」「沿用某成员的可见日历（历史绑定）」「家庭共享日历」。
- 附件按收件人目标落盘并记录在任务上：`snapshots/calendar-v{N}-user-<账号id>-upcoming.ics` 与 `snapshots/calendar-v{N}-family-upcoming.ics`；重试仍取该任务记录的不可变快照，发送前校验其 `sha256` 与 `attachment_hash` 一致，不一致就拒绝发送。
- 幂等键仍是 `(export_version, recipient_id)`，唯一约束在数据库层；每位收件人单独发送，避免在 `To` 或 `Cc` 中泄露其他收件人的地址；一个收件人失败不阻止其他人。
- **正文里的订阅地址（2026-10-12 起）**：只有**账号收件人**会在正文里看到地址，而且一定是他**自己**那条固定地址（`<基地址>/sisi_feed_….ics`，由服务端按账号重算，不依赖「只显示一次」的明文）；**外部邮箱（含单用户版升级上来的历史邮箱）一条地址都不给**，只提示地址在各自账号的「我的设置」里。正文里的范围说法随之区分：账号收件人写「你可见的日历(个人 + 家庭共享)」，历史外部邮箱写「<账号>可见的日历(个人 + 家庭共享)」，普通外部邮箱写「家庭共享日历」。并集地址与旧 `SUBSCRIPTION_URL` 已彻底取消。
- 把账号邮箱改成已被某条外部收件人占用的地址时，那条记录会被认领为账号收件人并保留历史发送时间；反之要维护他人邮箱时只能走管理员的外部收件人接口。

### 18.7 升级与启动引导

- `alembic upgrade head` 只做结构变更（第 18.2 节），不读写业务数据。
- 每次启动执行 `app/bootstrap.py::ensure_family_setup`，幂等地把数据库补齐成家庭版：
  1. 没有账号时创建首位管理员，沿用 `ADMIN_USERNAME` / `ADMIN_PASSWORD`（口令以 Argon2id 存储；
   凭据由环境给出时不强制改口令，只有在两者都留空、由系统随机生成口令时才把
   `must_change_password` 置为真）；
  2. 建他的私人日历；
  3. 没有共享日历时建一条家庭共享日历，默认名「家庭共享日历」，管理员是 `owner`、其余成员是 `viewer`；
  4. 给缺私人日历、缺成员关系或缺账号收件人的账号补齐；
  5. 把 `calendar_id IS NULL` 的历史事件全部回填进首位管理员的私人日历，并补上创建人；
  6. **每个账号都登记一条固定订阅地址**（`ensure_account_feed_token`，幂等；建号时已登记的账号原样返回，
    标签统一为「账号订阅地址(固定)」）。这既覆盖升级上来的老账号，也兜住「建号时拿不到 `settings`」的路径；
  7. **首次升级**时把历史外部收件人与历史 Agent 令牌绑定到首位管理员，保持它们原有的行为。
     历史外部收件人**只写 `scope_user_id`，不写 `user_id`**：`user_id` 是「账号收件人」的身份标记，
     每个账号最多一行，把多个邮箱都写进同一个 `user_id` 会让账号名下出现多行，取「唯一一行」的
     逻辑随即抛 `MultipleResultsFound`（真机升级踩过这个坑，见《部署与运维》§8.1 与
     `migrations/versions/0006_recipient_scope.py`）。写范围列既保住了收信范围，又不占用身份列。
- 结论：升级后「原有日程 = 首位管理员的私人日历内容」，既有收件人的收信范围保持不变；**旧的无令牌订阅地址不再提供服务**（2026-10-12 起），升级上来的账号首次启动就拿到自己的固定地址。已有家庭数据时引导不产生任何副作用。

### 18.8 缺陷修复：邮件附件的缺省查询起点

`build_range` 的缺省查询起点原先用 **UTC 的今天**去套当地零点。在 UTC+10（本部署的默认时区 `Australia/Brisbane`）这类时区里，当地刚过午夜时「今天」会被算成前一天，于是「昨天」的全天事件会被重新放进邮件附件。

现已改为按**应用默认时区的当地今天**计算起点，全天事件仍按当地日期判断（第 18.1 节的时间不变量不变）。该修复只影响邮件专用快照的取数范围，发布文件与版本快照保持完整。

#### 18.11.3 前缀必须与 Tailscale Serve 的挂载路径一致

- Serve 命令：`tailscale serve --bg --yes --https=443 --set-path=/calendar http://127.0.0.1:443/calendar`，
  `--set-path` 与目标 URL 里的路径、以及 `PUBLIC_BASE_URL` 的路径部分**三者逐字相同**。
- 本仓库的用法**不依赖前缀剥离**：外部的 `/calendar` 与后端的 `/calendar` 是同一个入口，
  应用把同一套路由注册两遍（裸路径 + `PUBLIC_BASE_URL` 的路径前缀，后者 `include_in_schema=False`），
  并由中间件按**当次请求**绑定前缀渲染链接。因此改前缀只需要同步改 Serve 与 `PUBLIC_BASE_URL`。
- 部署自检：`/calendar/login` 返回 `200`；`/calendar` 本身返回 `404` 纯文本（说明订阅命名空间没被
  管理页污染、旧的无令牌地址也真的取消了）；本机 `http://localhost:443/admin` 仍能登录。
- 把 `PUBLIC_BASE_URL` 配成**不含路径**的域名（如 `https://calendar.example.test`）时，整套前缀路由
  自动退回裸路径，不会留下半个 `/calendar` 面。

#### 18.11.4 已知取舍

- **轮换 `data/session_secret`（或改 `SESSION_SECRET`）会让所有账号的固定订阅地址同时失效**，
  也会让所有尚未使用的验证码哈希一起失效。这不是缺陷而是刻意的取舍：密钥即身份，固定地址之所以
  能长期显示、随时重发，正是因为它是由这把密钥派生出来的。轮换后每人需要重新从「我的设置」抄一次
  地址、并重新验证邮箱；历史邮件里的地址会变成 `404`。
- 固定地址**只存哈希、不可撤销**：地址一旦外泄只能通过轮换密钥来作废（见上一条），因此正文与页面都
  提醒「地址等同于密码，不要转发」。需要可单独撤销的地址时，用「我的设置」里的临时地址。
- 验证码走 SMTP，SMTP 未配置时注册仍然成功、但验证码发不出去，账号只能停在验证页，由页面提示
  「重新发送」；首位管理员不受影响。

### 18.12 邮箱验证（2026-10-12）

`app/email_verify.py` 提供验证码的生成、校验与两封通知信（`app/mailer.py::send_verification_code`
与 `::send_subscription_address`），路由在 `app/routers/auth.py`。

规则：

| 项目 | 取值 | 说明 |
|---|---|---|
| 验证码 | 6 位数字（允许前导零，一律按字符串比较） | `app/email_verify.py::CODE_LENGTH` |
| 有效期 | 默认 30 分钟（`EMAIL_CODE_TTL_SECONDS`） | 过期返回「验证码已过期,请点「重新发送验证码」」 |
| 最大尝试 | 默认 5 次（`EMAIL_CODE_MAX_ATTEMPTS`） | **第 5 次错误直接作废**验证码，必须重新发送 |
| 重发冷却 | 默认 60 秒（`EMAIL_CODE_RESEND_SECONDS`） | 冷却期内重发返回 `429` 与剩余秒数 |
| 入库形式 | `HMAC(session_secret, "verify:<账号id>:<验证码>")` | 库里**没有明文**；重发换新码并清零尝试次数，旧码立即失效 |
| 收件人 | 账号自己的 `users.email` | 邮件里同时给出 `<基地址>/verify-email` 入口与有效期说明 |

闸门（`app/deps.py::_gate_verification` → `EmailNotVerified`）：

- **有邮箱但未验证**的非管理员：所有业务页面 `303` 到 `<前缀>/verify-email`；所有 `/api` 返回
  `403` 与错误码 `email_not_verified`。验证页本身与「重新发送」不受闸门影响，否则会把自己挡在门外。
- **首位管理员豁免**：本机救急时不能因为邮箱没验证就被锁在门外。
- **没有邮箱的账号不受阻**（升级上来的老账号可能没填），由界面持续提醒补填。
- **未验证不成为邮件收件人**：`app/accounts.py::sync_user_recipient()` 只认「有邮箱**且**已验证」的账号；
  验证通过时会同步一次，把账号收件人建起来。

流转：

1. 注册表单必须填邮箱（缺邮箱 `422`）→ 建号 → 立刻发验证码 → 跳转
   `<前缀>/verify-email?sent=1`（发信失败则 `sent=0` 并提示重发）。
2. 登录时若账号待验证，登录成功后被直接送到验证页，不在别处碰壁。
3. 验证页有三个动作：提交验证码、重新发送（60 秒冷却）、改邮箱后重发
   （`POST /verify-email/email`，用于注册时写错地址）。
4. 验证通过：置 `email_verified_at`、清空验证码字段、建账号收件人，并**补发一封
   「你的固定订阅地址」邮件**，然后 `303` 到 `/admin/me` 提示「邮箱已验证,固定订阅地址已发到你的邮箱」。
5. 改邮箱（无论走「我的设置」还是验证页）：立刻打回待验证并重发新码。

安全：

- 验证码与固定订阅地址明文**只出现在邮件正文**里；日志、审计 `detail`、数据库都不得出现明文，
  数据库里只有 HMAC 与 `sha256`。发信失败只记 `type(exc).__name__`，不带正文。
- 验证码按账号绑定（HMAC 的键含 `user_id`），因此两个账号拿到同一个数字也不会互相验证成功。

### 18.13 固定订阅地址（2026-10-12）

`app/feed_tokens.py` 负责派生与登记，`app/routers/pages.py` 的「我的设置 → 我的订阅地址」与
`app/routers/feed.py` 的订阅入口是它的两端。

派生与登记：

```text
token = "sisi_feed_" + HMAC(session_secret, "feed:<账号id>")[:40]      # 40 位 hex = 160 bit
库里  token_hash = sha256(token)      # 只有哈希;明文随时可由服务端重算
```

- **登记时机**：`app/accounts.py::create_user(settings=...)`（建号）与
  `app/bootstrap.py::ensure_family_setup`（每次启动兜底，覆盖升级上来的老账号）都调用
  `ensure_account_feed_token()`，**幂等**：已有记录就原样返回（并把标签统一成「账号订阅地址(固定)」）。
  建号时若拿不到 `settings`，由引导那次补齐。
- **永不变更**：同一个账号永远得到同一条明文，因此「我的设置」可以长期显示、
  验证通过后可以邮件告知、忘了随时再看一眼——不需要保存明文。
- **不能停用/撤销**：固定地址是订阅端长期填着的那条，误撤销会让全家人的手机一起断更；
  对它的停用与撤销请求返回 `409`。要换地址只能轮换服务端密钥（见第 18.11.4 节）。
- **临时地址仍然可用**：账号在同一个页面生成的随机令牌走旧路径（明文只显示一次、可单独停用/撤销、
  撤销后立刻 `404`），适合临时给某台设备或链接外泄时替换。
- **失效方式**：轮换 `data/session_secret` 会让所有固定地址与新验证码一起失效；
  停用或删除账号会让该账号的地址与订阅目标一并消失（见第 18.3、18.4 节）。
- **范围不变**：固定地址仍然只服务该账号可见日历（私人 + 家庭共享）的合并结果
  （`export/feeds/user-<账号id>.ics`），既不是全库并集，也不是首位管理员的可见范围。
