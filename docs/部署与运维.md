# 部署与运维

本文覆盖 Docker Desktop 部署、Tailscale Serve 暴露订阅入口、备份恢复、升级回滚与故障排查。

对应开发文档第 9、10、12 节。设计文档里的 `http://localhost:443/admin` 是**本机管理地址**,
端口号虽然是 443,容器内外都走 HTTP,HTTPS 由 Tailscale 在外层终止。

---

## 1. 前置条件

| 项目 | 要求 |
|---|---|
| 操作系统 | Windows + Docker Desktop,**或 Linux/NAS + Docker Engine** |
| Docker | 24 以上,含 Compose v2(`docker compose version` 可用) |
| Tailscale | 可选;本文示例节点为 `sisi-laptop.tail921448.ts.net` |
| 端口 | 默认 Compose 仅绑定 `127.0.0.1:443`;NAS 端口冲突时见 §2.4.1 |
| 磁盘 | `/data` 所在盘预留空间;必须是可靠支持文件锁的本地磁盘 |
| 账号 | 家庭版 3–5 人各一个账号:每人一条**只有本人可见**的私人日历,外加一条全家共享的日历 |

> 本文自 2026-10-08 起按**家庭多人版**编写。从单用户版升级时日程数据无需重建,
> 旧的无令牌 `/calendar` / `/calendar.ics` 已取消。原有两位测试用户已人工改用固定地址,
> 本轮不保留旧地址兼容,也不再安排订阅迁移操作。见 §5.3。

## 2. 首次部署

### 2.1 准备配置文件

```powershell
cd D:\桌面\sisi_apps\SisiCalendar
Copy-Item .env.example .env
notepad .env
```

Linux/NAS 上等价的命令:

```bash
cd /volume1/docker/sisi-calendar   # 按 NAS 的实际共享卷路径修改
cp .env.example .env
chmod 600 .env
```

至少确认以下项:

```dotenv
DATA_DIR=/data
ADMIN_USERNAME=admin
# 推荐:先算出哈希再填,避免明文口令进入 .env
# ADMIN_PASSWORD_HASH=$argon2id$v=19$m=65536,t=3,p=4$....
SESSION_SECRET=            # 留空则首次启动自动生成并写入 /data/session_secret
DEFAULT_TIMEZONE=Australia/Brisbane
# 公开面的正式基地址(**含路径前缀**):注册/登录/管理/订阅地址都挂在它下面
# 路径部分必须与 Tailscale Serve 的 --set-path 完全一致(见第 3 节)
PUBLIC_BASE_URL=https://calendar.example.com/calendar
# 邮箱验证码:有效期(秒)/ 允许的错误次数 / 重发冷却(秒),一般不用改
EMAIL_CODE_TTL_SECONDS=1800
EMAIL_CODE_MAX_ATTEMPTS=5
EMAIL_CODE_RESEND_SECONDS=60
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USERNAME=you@example.com
SMTP_PASSWORD=应用专用密码
SMTP_FROM_ADDRESS=you@example.com
```

生成管理员口令哈希(明文不会写入任何文件):

```powershell
uv run python -m app.cli hash-password
```

> 如果既没有 `ADMIN_PASSWORD_HASH` 也没有 `ADMIN_PASSWORD`,首次启动会随机生成口令并
> **只在容器日志里打印一次**,同时把哈希写入 `/data/admin.hash`。错过日志就用
> `docker compose exec calendar python -m app.cli credential` 查看来源,或重新注入哈希。

### 2.2 启动

```powershell
docker compose up -d --build
docker compose logs -f calendar
```

启动流程会自动完成:`/data` 目录准备 → Alembic 迁移到最新版本 → 数据库与 ICS 一致性检查
→ 恢复中断的发信任务 → 启动后台任务(每分钟修复 ICS、轮询邮件队列)。

默认 Compose 配额为 `256 MiB` 内存、`0.50 CPU` 和 64 个进程/线程。该配额面向单用户、
单 Uvicorn 进程部署，并为启动迁移、ICS 导出和邮件附件构造保留峰值余量。若出现容器被
OOM 杀死，应优先调高 `mem_limit`，不要关闭健康检查或数据一致性任务。

### 2.3 本机验证

```powershell
curl.exe -i http://localhost:443/healthz
curl.exe -i http://localhost:443/readyz
curl.exe -i http://localhost:443/login            # 本机登录页(裸路径)
curl.exe -i http://localhost:443/calendar/login   # 家人用的登录页(带前缀)
curl.exe -i http://localhost:443/calendar         # 期望 404 + text/plain(旧的无令牌地址已取消)
```

- `/healthz` 返回 `{"status":"ok"}` 表示进程存活。
- `/readyz` 返回 `200` 且 `checks` 全为 `ok` 表示数据库、数据目录与导出状态都正常。
- 订阅是不是好的,要拿**具体某人的固定地址**来试:`/admin/me` 页面上复制
  `http://localhost:443/calendar/<令牌>.ics`,期望 `Content-Type: text/calendar; charset=utf-8`。
  前缀根本身 `/calendar` 从本轮起只回 404 纯文本。

浏览器打开 `http://localhost:443/admin` 登录后应看到月历视图。

### 2.4 关闭对外暴露(重要)

Compose 里端口必须写成 `127.0.0.1:443:8000`。一旦省略主机 IP,Docker 会绑定 `0.0.0.0`,
管理界面就会出现在局域网中。可用下面的命令确认绑定地址:

```powershell
docker compose ps
netstat -ano | findstr :443
```

`netstat` 结果应只出现 `127.0.0.1:443`,不应出现 `0.0.0.0:443` 或 `[::]:443`。

#### 2.4.1 Linux/NAS 的端口、目录与权限

NAS 的 443 端口通常已被管理界面或反向代理占用,可以把 `compose.yaml` 的宿主端口改成
高位端口,例如:

```yaml
ports:
  - "127.0.0.1:18443:8000"       # 仅 NAS 本机代理/Tailscale 可访问
```

若确实要让局域网设备直连,可绑定 NAS 的**固定局域网 IP**,例如
`192.168.1.20:18443:8000`;这会同时向局域网暴露管理面,应配合防火墙或反向代理访问控制。
不要只写 `18443:8000`,否则 Docker 会绑定所有网卡。

镜像以非 root 用户 `10001:10001` 运行。首次启动前先准备持久化目录:

```bash
mkdir -p data
sudo chown -R 10001:10001 data
docker compose up -d --build
```

`data/` 应放在 NAS 本地 ext4/Btrfs 卷上,不要把 SQLite 主库放进 SMB/NFS 网络挂载。
只有本地反向代理时继续绑定 `127.0.0.1`;反向代理生成的公开地址必须与
`PUBLIC_BASE_URL`(含 `/calendar` 路径前缀)完全一致。

### 2.5 配置邮件发信(多成员部署必需)

邮件同步本身可以关闭:没有配置 SMTP 时,保存日程不会创建发信任务,订阅与 ICS 仍然正常。
但是**邀请新成员时 SMTP 是必需项**:注册必须填邮箱,新成员需要收取 6 位验证码;
验证前会被挡在验证页面。只有首位管理员自用、不邀请成员时才可以不配 SMTP。

#### 需要的环境变量

| 变量 | 必填 | 说明 |
|---|---|---|
| `SMTP_HOST` | 是 | 发信服务器地址 |
| `SMTP_FROM_ADDRESS` | 是 | 发件人邮箱。**与 `SMTP_HOST` 同时存在才算「已配置」** |
| `SMTP_PORT` | 否 | 默认 `587`(STARTTLS);SSL 一般用 `465` |
| `SMTP_SECURITY` | 否 | `starttls`(默认)/ `ssl` / `none` |
| `SMTP_USERNAME` | 否 | 留空则不认证(仅内网中继适用) |
| `SMTP_PASSWORD` | 否 | **应用专用密码 / 授权码**,不是邮箱登录密码 |
| `SMTP_FROM_NAME` | 否 | 显示名,默认 `Sisi Calendar` |
| `SMTP_TIMEOUT_SECONDS` | 否 | 默认 30 |
| `MAIL_MAX_ATTEMPTS` | 否 | 默认 5 次 |
| `MAIL_BACKOFF_MINUTES` | 否 | 默认 `1,5,15,60,180` |

当前实现只直接读取 `SMTP_PASSWORD` 环境变量(没有 `SMTP_PASSWORD_FILE` 接口):
口令不写数据库、不进日志、界面只显示「已注入/未注入」。
`.env` 已被 `.gitignore` 排除,不要提交。

#### 常见邮箱服务商

| 服务商 | HOST | 端口 / 安全方式 | 用户名 | 口令 |
|---|---|---|---|---|
| Gmail | `smtp.gmail.com` | 587 / `starttls` | 完整邮箱地址 | **应用专用密码**(需先开两步验证) |
| QQ 邮箱 | `smtp.qq.com` | 465 / `ssl` | 完整邮箱地址 | **授权码**(设置 → 账户 → 开启 SMTP) |
| 163 邮箱 | `smtp.163.com` | 465 / `ssl` | 完整邮箱地址 | **授权码** |
| Outlook / M365 | `smtp.office365.com` | 587 / `starttls` | 完整邮箱地址 | 应用密码(开了两步验证时) |
| iCloud | `smtp.mail.me.com` | 587 / `starttls` | 完整邮箱地址 | **App 专用密码** |
| 自建 Postfix | 你的域名 | 587 / `starttls` | 视配置 | 视配置 |

> 用主账号密码通常会被拒绝(报 `SMTPAuthenticationError`),务必用应用专用密码或授权码。

#### 生效与验证

```powershell
# 1. 写入 .env(注意用引号包住含特殊字符的口令)
notepad .env
#   SMTP_HOST=smtp.qq.com
#   SMTP_PORT=465
#   SMTP_SECURITY=ssl
#   SMTP_USERNAME=you@qq.com
#   SMTP_PASSWORD=你的授权码
#   SMTP_FROM_ADDRESS=you@qq.com
#   SMTP_FROM_NAME=Sisi Calendar

# 2. 重建容器让环境变量生效(改 .env 不会改变已存在容器的环境)
docker compose up -d --force-recreate

# 3. 打开设置页验证
start http://localhost:443/admin/settings
#   「SMTP 发信配置」应显示「已配置」
#   先点「测试连接 / 发送测试邮件」(留空收件地址 = 只测连接)
#   再填自己的邮箱点一次,确认能收到
```

设置页上的 SMTP 区块是**只读**的——出于安全考虑,凭据只能在 `.env` 里改。
发邀请码之前,必须在设置页先做一次「测试连接」,再向自己的邮箱发一封测试信。

#### 添加收件人并发出第一封

1. 在 `/admin/settings` 的「邮件收件人」里填邮箱,勾选隐私确认后点「添加」。
   这里添加的是**外部邮箱**,只收家庭共享日历范围,不会收到任何人的私人日程或订阅地址。
   这张表**只**管外部邮箱:成员的账号邮箱在下方「账号邮箱(自动同步)」里只读列出
   (状态会写明`自动同步中` / `邮箱待验证` / `未填邮箱` / `账号已停用,不收信`)。
2. 设置同步人员本身不会发信。要让对方立刻拿到当前(未来)日程,去 `/admin/sync` 点
   「向当前人员发送最新版」(会二次确认)。
3. 之后每次在界面上「保存并同步」,或通过 Agent 接口新建日程,都会自动向**看得见这次改动**的
   启用人员各发一封带 `calendar.ics` 的邮件(手动群发不受此筛选影响,发给全部启用人员)。

> 有账号的家庭成员**不用在这里添加**:本人的邮箱验证通过后会自动成为
> **账号收件人**(`sync_account_recipients` 在启动、发信前与设置页渲染前对齐),
> 只收到自己可见范围里尚未结束的日程。这一行**不能**在设置页或
> `/api/v1/sync-recipients` 里删除/停用(都是 `409`);要让某个账号停止收信,
> 请到「成员」页**停用该账号**(重新启用即自动恢复)。

> **邮件附件只含尚未结束的日程**:附件是该版本中「还没结束」的事件——正在进行与仍在重复的
> 日程都在,已经结束的一律不在(包括今天早些时候刚结束的)。完整历史(含过去事件)始终可以从
> 长期订阅地址获得——发布文件 `calendar.ics` 不做任何过滤。
>
> 邮件正文里的「事件时间」按**你提交时间所带的偏移量**表述(如 `14:00–15:00(UTC+11:00)`):
> 快捷指令带着 `+11:00` 提交,正文就写你输入时的钟点;而事件的参照时区(默认时区或
> `timezone` 字段)决定它在日历与 ICS 里怎么显示。网页表单的时间框不带偏移量,所以从
> `/admin` 建的事件仍按事件时区表述。

> 注意:配置 SMTP 之前产生的历史日程不会补发。上面的「发送最新版」就是为此准备的——
> 它会把当前尚未结束的日程发给所有启用人员各一次。

#### 失败时的表现

- 每位收件人**单独发送**:一个人失败不影响其他人。
- 失败按 `1,5,15,60,180` 分钟退避重试,达到 `MAIL_MAX_ATTEMPTS` 后标记为失败。
- `/admin/sync` 的邮件队列表格逐条显示**发起人**(触发这次变更的账号,手动同步与历史任务显示
  `—`)、**操作时间**(任务创建时刻)、**发送时间**、重试次数、
  下次重试时间与错误摘要,并支持逐条手动重试。时间按日历默认时区显示(鼠标悬停可看秒)。
- **邮件正文里「发起人」只加在具体日程的增删改上**(新增/修改/删除日程),手动同步
  (「重新生成 ICS」「向当前人员发送最新版」)不写这一行;升级前的历史任务写「未记录」。
  正文用的是**发信那一刻**的账号显示名,队列表格里的是**建任务那一刻**的快照。
- 附件永远取自该任务记录的不可变快照:即使中间又改了几次日历,重试发的仍是那一版,
  不会「冒充新版」。
- 邮件失败**不会**回滚日程或 ICS,也不会影响订阅。

#### 邮件排错

| 现象 | 原因与处理 |
|---|---|
| 设置页一直显示「未配置」 | `SMTP_HOST` 或 `SMTP_FROM_ADDRESS` 为空;或改了 `.env` 没重启容器 |
| `SMTP 认证失败` | 用了登录密码而不是授权码/应用专用密码;或该邮箱未开启 SMTP 服务 |
| `无法连接 SMTP 服务器` | 主机名或端口写错;端口被网络/防火墙拦截;`SMTP_SECURITY` 与端口不匹配 |
| 证书校验失败 | 服务器证书不受信任(常见于自建中继)。**不要**关闭校验;改用受信任证书或换端口 |
| 全部成功但收不到 | 进了对方垃圾箱;检查发件域名的 SPF/DKIM |
| 只有个别人失败 | 单个地址被对方服务器拒收;修正后在该行点「重试」 |

### 2.6 日历设置(默认时区)

`/admin/settings` 的「默认时区」是下拉框,按地区分组列出 30 个常用时区,每项前面是**序号**:

```text
亚洲   1. 北京时间(Asia/Shanghai)      11. 悉尼时间(Australia/Sydney)
       2. 香港时间(Asia/Hong_Kong)     12. 布里斯班时间(Australia/Brisbane)
       …                                 …
```

- 序号顺序**固定不变**(只会在表尾追加),所以可以放心把它写进快捷指令或脚本;
  `timezone` 字段填序号、中文名或 IANA 名都行。
- 下拉框只放常用时区;环境配置里写过的其它 IANA 名(如 `Asia/Kathmandu`)会作为
  「当前值,不在常用清单中」保留在选项里,不会被静默改掉。
- 新建/编辑日程页的时区输入框也接受序号与中文名,悬浮候选里能看到同样的编号。
- 完整清单与解析规则见 [`docs/static/app-timezones.md`](static/app-timezones.md)。

### 2.7 家庭版的首次启动引导(2026-10-08 新增)

家庭版只需要一个**新增**(其实是替换)的环境变量:`PUBLIC_BASE_URL`(原 `SUBSCRIPTION_URL`,
2026-10-11 改名为公开面基地址并带路径前缀);`ADMIN_USERNAME`/`ADMIN_PASSWORD`
(或 `ADMIN_PASSWORD_HASH`)的语义不变。首次启动除迁移之外,还会执行一次**幂等**的引导
`app/bootstrap.py::ensure_family_setup`,把数据库补齐成家庭版;重复启动不会产生任何副作用。

引导会完成:

1. 用 `ADMIN_USERNAME`/`ADMIN_PASSWORD`(或 `ADMIN_PASSWORD_HASH`)创建**首位管理员**
   ——整个部署里的「家长」账号;若口令是启动时随机生成的,这个账号带 `must_change_password`;
2. 给他建一条**私人日历**(`calendars.kind = 'personal'`,归属这个账号);
3. 建一条**家庭共享日历**(`calendars.kind = 'shared'`,默认名「家庭共享日历」):
   他是 `owner`,之后加入的成员默认是 `viewer`(只读);
4. 建立成员关系与他的**账号收件人**(`sync_recipients.user_id` 指向他,邮箱即 `users.email`);
5. 把历史数据挂到他名下:所有 `calendar_id IS NULL` 的事件回填进首位管理员的私人日历,
   历史外部收件人与历史 Agent 令牌绑定到首位管理员;
6. (2026-10-11 起)给**每个**已有账号登记一条**固定订阅地址**(`feed_tokens` 里标签为
   「账号订阅地址(固定)」的那行,只存哈希)。

因此**升级后「原有日程」就是首位管理员的私人日历内容**,条数、UID 与版本语义都不变。

- 迁移 `migrations/versions/0005_family_accounts.py` 只做**结构变更**(新建
  `users`/`calendars`/`calendar_members`/`invite_codes`/`feed_tokens`,给
  `events`/`sync_recipients`/`agent_tokens` 加列);数据回填全部由引导完成,
  结构变更与数据回填分开,重复启动才安全;
- 历史外部收件人**只绑收信范围**:引导只写 `scope_user_id = 首位管理员`,`user_id` 保持为空
  ——`user_id` 是「账号收件人」的身份标记,每个账号只能有一行(迁移 `0006_recipient_scope` 起);
- 引导只补缺,不覆盖已有的账号、日历或成员关系;
- 若 `readyz` 正常但订阅入口返回 503,通常意味着库里还没有首位管理员(引导未完成):
  看一次容器日志即可确认。

### 2.8 让家人加入(2026-10-11 新增)

家人自己加入只需要一条 tailnet 内可达的注册地址:

1. 首位管理员登录 → **成员** → 邀请码 → 生成:页面直接给出**可复制粘贴的完整邀请链接**
   `https://<节点>/calendar/register?code=<邀请码>`(明文只显示一次);
2. 把这条链接发给家人(本轮真机地址形如
   `https://sisi-laptop.tail921448.ts.net/calendar/register?code=sisi_invite_...`);
3. 家人在自己的设备上打开该链接注册。**注册必须填邮箱**:提交后系统立刻发一封 6 位验证码邮件,
   注册成功但会停在 `/calendar/verify-email`,填对验证码后才能用日历;
4. 验证通过时会**自动**补发一封「你的固定订阅地址」邮件;这条地址在**账号创建时就已生成**,
   永远不变,也可以在**我的设置 → 我的订阅地址**里随时查看
   (`https://<节点>/calendar/<自己的固定令牌>.ics`)。订阅地址一律绑定账号本人,
   管理员不能替成员生成或查看,所以这一步由本人完成(或直接用那封邮件里的地址);
5. 想一起编辑家庭共享日历的人,由管理员在**成员 → 共享日历与权限**里把角色提升为
   `editor`(新成员默认只读 `viewer`)。

> 注册与登录地址都在**公开面前缀**下:`https://<节点>/calendar/register?code=<邀请码>`、
> `https://<节点>/calendar/login`(页面里的链接也都会带这个前缀),所以 Tailscale Serve 只需挂
> `/calendar` **一段**(见 §3)。本机排障时可以走裸路径 `http://localhost:443/register`。

## 3. Tailscale Serve:只对外挂 `/calendar` 一段(2026-10-11 更新)

> **警告一**:`tailscale serve` 是**整机配置**。在已有路由的机器上操作前必须先保存快照,
> 避免误删其他入口。
>
> **警告二**:挂载路径必须与 `PUBLIC_BASE_URL` 的**路径部分逐字一致**(默认 `/calendar`)。
> 应用里的链接按**当次请求的前缀**渲染:从 `/calendar/login` 进来的页面里全是 `/calendar/...`,
> 本机裸路径进来的仍是裸路径;绝对地址(邀请链接、订阅地址、邮件正文)一律取自
> `PUBLIC_BASE_URL`。本仓库的用法**不依赖前缀剥离**——`--set-path=/calendar` 配
> `http://127.0.0.1:443/calendar`,外部的 `/calendar` 与后端的 `/calendar` 是同一个入口。
> 这不是假设:首次部署时用不带路径的目标实测,`/calendar/login` 返回了 200(登录页),
> 说明订阅命名空间被管理页污染了。

### 3.0 暴露口径(2026-10-11 决定,同日收紧为「只挂 /calendar」)

成员面是**故意**对 tailnet 开放的,但只开放 `/calendar` 一段:

| 对外地址 | 谁用 |
|---|---|
| `/calendar/login`、`/calendar/register` | 家人登录 / 用邀请链接注册 |
| `/calendar/admin/...` | 家人自助改资料、看自己的固定订阅地址(管理功能对成员 403) |
| `/calendar/verify-email` | 新注册成员填邮箱验证码 |
| `/calendar/<令牌>.ics` | iPhone 等订阅端(每人一条固定地址) |
| `/calendar/static/...` | 页面用的 CSS/JS |
| `/`、`/dsh` | DSH 自己的界面,与本服务无关 |
| `/agent` | 远程 Agent(Bearer-only,可选,默认整段 404) |

**不要再挂裸 `/login`、`/logout`、`/register`、`/admin`、`/api`、`/static`**:登录、注册与
管理界面全在 `/calendar` 前缀下,裸路径只在**本机**(`http://localhost:443/...`)使用,
给管理员上机排障。权限边界仍然是**账号 + 角色**:成员访问 `/admin/members`、
`/admin/settings`、`/admin/sync` 与相关 API 返回 **403**。

```powershell
# 1. 先看现状并留存
tailscale serve status | Tee-Object -FilePath tailscale-serve-backup.txt

# 2. 只保留这几个挂载(目标是本机回环地址,不是 tailnet 域名)
tailscale serve --bg                                  http://127.0.0.1:3081
tailscale serve --bg --set-path=/dsh                  http://127.0.0.1:3081
tailscale serve --bg --set-path=/agent                http://127.0.0.1:443/api/agent   # 仅开远程 Agent 时
tailscale serve --bg --set-path=/calendar             http://127.0.0.1:443/calendar
# 旧别名 /calendar.ics 只为「让它也回同一句 404 纯文本」而挂;不挂的话它会被 `/` 接走,
# 变成 DSH 的 401 JSON(同样不可用,但排障时容易被误读成「日历服务坏了」)
tailscale serve --bg --set-path=/calendar.ics         http://127.0.0.1:443/calendar.ics

# 3. 从旧布局(挂了裸 /login、/admin、/api、/static 等)改过来时,先清空再按第 2 步重挂。
#    注意 reset 会同时清掉 / 与 /dsh,必须在同一条命令序列里补回来:
#    tailscale serve reset
```

### 3.2 ACL 建议

在 tailnet ACL 中只允许指定用户或设备访问该节点的 Serve:

```jsonc
{
  "acls": [
    // 只有自己的设备可以访问 sisi-laptop 的 Serve 服务
    { "action": "accept", "src": ["autogroup:member"], "dst": ["sisi-laptop:443"] }
  ]
}
```

按需收紧到具体设备标签。**不要**启用 `tailscale funnel`——那会把私人日历暴露到公网。

本轮起成员面是故意开放的(见 §3.0),ACL 仍是外层边界:它只能把「谁能连到这个节点」
收紧到自己的设备,并不能区分账号;账号级边界由登录与角色判定负责,两者不可互相替代。

### 3.3 iPhone 订阅

1. iPhone 打开 Tailscale 并确认已连接。
2. 设置 → 日历 → 账户 → 添加账户 → 其他 → 添加已订阅的日历。
3. 服务器填**你自己的固定订阅地址** `https://sisi-laptop.tail921448.ts.net/calendar/<你的令牌>.ics`
   (在 `/calendar/admin/me` 的「我的订阅地址」里复制,或从邮箱验证通过后收到的那封邮件里复制)。
4. 关闭 Tailscale 时系统日历保留最后一条缓存;恢复连接后自动拉取新版本。

#### 家庭版:每人一条**固定**订阅地址(2026-10-11 起)

登录 → **我的设置 → 我的订阅地址**,面板最上面那条「**账号订阅地址(固定)**」就是本人的地址:
`https://<host>/calendar/<令牌>.ics`,内容是**该账号可见的日历**(个人日历 + 他能看到的家庭共享日历)。

- 这条地址在**账号创建时就已确定**,由服务端密钥派生
  (`token = sisi_feed_ + HMAC(session_secret, "feed:<账号id>")[:40]`),**永远不变**;
  随时可以回到页面查看,也可以在验证邮箱时收到的那封邮件里找到。
  界面上**不提供停用/撤销**(点会返回 409),因为它就是订阅端长期填着的那一条。
- **升级前的无令牌地址 `https://<host>/calendar` 已经失效**(返回 404 纯文本)。
  既有 iPhone 订阅必须换地址:设置 → 日历 → 账户 → 订阅的日历 → 删掉旧的,
  用上面那条固定地址重新添加。
- 面板里还可以额外建**临时地址**:明文只在创建那一次显示,可随时停用/撤销,
  适合临时发到别的设备试一次。
- 家庭共享范围另有一类**家庭订阅地址**(令牌的 `user_id` 为空,在**家庭成员 → 家庭订阅地址**
  里生成):它**只导出家庭共享日历**,不含任何人的私人日程,适合放在公用设备(客厅平板)
  或给没有账号的长辈;建议每位订阅者单独建一条,外泄时只撤销那一条。
- **不要轮换 `data/session_secret`**:那会让所有固定地址与所有验证码哈希一起失效(见 §8.2)。

订阅日历是**只读**的,这一点决定了提醒的可见行为:

- 事件里的提醒会导出成 `VALARM`(`TRIGGER:-PT15M` 这类相对时长)。iPhone 日历对**订阅日历**
  的通知由本地设置决定(设置 → 日历 → 默认提醒时间,或该订阅账户上的开关),系统并不会
  保证按每条 `VALARM` 逐条弹通知;把同一份 `calendar.ics` 导入到支持 `VALARM` 的客户端
  (macOS 日历、Thunderbird、Google 日历导入)时,才会按事件里配置的提醒触发。
- 想改提醒,在 `/admin/events/{id}` 里勾选或填自定义分钟数即可,保存后会重新生成 ICS。
- 「备注」在订阅端表现为事件说明(说明字段),「链接」表现为事件的 URL;iPhone 事件详情页
  可以看到,但订阅日历不能在手机上编辑。

### 3.4 远程 Agent 接入(可选,默认关闭)

让本机之外的脚本 / LLM Agent / 快捷指令通过 HTTP 新建日程。

**默认是关闭的**:只要**两个来源都没有令牌**——`.env` 的 `AGENT_API_TOKEN` 为空,且平台内也没有
启用的令牌——`/api/agent` 全路径返回 404,等同不存在。
这是一个**可写的**对外接口,开启前请想清楚下面三点:

1. 拿到令牌的人就能往你的日历里写日程(并能给所有同步人员触发邮件)。
2. 令牌有两个来源,**取并集**:平台内创建的令牌(只存哈希,明文只在生成时显示一次)与
   `.env` 里的 `AGENT_API_TOKEN`(明文注入,可逗号分隔多个)。`.env` 那一路作为兜底保留:
   数据库损坏或忘记在平台上建令牌时仍能应急。
3. 接口只认 `Authorization: Bearer`,**不接受 Cookie 会话**,因此没有 CSRF 面;
   反之,浏览器里已登录的管理会话也不能调用它。

#### 在平台内管理令牌(推荐)

登录后进入 **设置 → 远程接入令牌**:

| 操作 | 说明 |
|---|---|
| 生成令牌 | 填名称(如「iPhone 快捷指令」)并勾选确认 → 页面显示**一次性明文**,复制后离开即无法再查看 |
| 改名 | 随时改,不影响令牌本身 |
| 停用 / 启用 | 临时冻结而保留记录;停用后下一次请求即 401 |
| 撤销 | 永久删除,不可恢复;撤销最后一枚令牌后 `/api/agent` 回到 404 |

安全约定:

- 数据库里**只保存 `sha256(token)` 哈希**,明文不进库、不进日志、不回显;
- 列表只显示**指纹**(哈希前 16 位),与审计日志里的 `agent:<指纹>` 一一对应,
  可据此判断是哪枚令牌在建日程;
- 令牌丢失(没复制到)时无法找回,只能撤销后重建;
- 该接口需要**登录 + CSRF**,匿名访问会被重定向到登录页。

#### 环境变量兜底(.env 路线)

不打算用平台界面时,也可以继续只用 `.env`;两处令牌同时有效。

#### 开启步骤

```powershell
# 1. 生成令牌并写入 .env(不要提交到版本库)
$token = python -c "import secrets;print(secrets.token_urlsafe(32))"
Add-Content .env "`nAGENT_API_TOKEN=$token"
docker compose up -d

# 2. 本机先自测(不经过 Tailscale)
#    请求体先写成无 BOM 的 UTF-8 文件,再用 --data-binary 发出去:
#    中文不会被控制台代码页破坏,也绕开各 shell 对 -d 里引号的不同解释。
$payload = @{
  title      = '本机自测'
  start_at   = '2026-11-03T14:00:00'
  end_at     = '2026-11-03T15:00:00'
  client_ref = 'smoke-1'
} | ConvertTo-Json -Compress
$body = Join-Path $env:TEMP 'sisi-agent-smoke.json'
[System.IO.File]::WriteAllText($body, $payload, [System.Text.UTF8Encoding]::new($false))

curl.exe -s -o NUL -w "HTTP %{http_code}`n" -X POST http://localhost:443/api/agent/events `
  -H "Authorization: Bearer $token" -H "Content-Type: application/json" `
  --data-binary "@$body"

# 期望 HTTP 201;若打印 200,说明这个 client_ref 之前已经建过(幂等重放,不是错误)。

# 3. 需要远程访问时,再追加 Serve 路由(同样要注意目标要带路径)
tailscale serve --bg --yes --https=443 --set-path=/agent http://127.0.0.1:443/api/agent
```

上面第 1、2 步必须整段粘进 **PowerShell**,不要拆开粘到别的 shell。`-d` 的写法在两种 shell 里正好相反,
用混了都不会只打印一个状态码:

| shell | 请求体写法 | 用错另一种写法的后果 |
|---|---|---|
| PowerShell | `-d '{\"title\":\"smoke\"}'`(单引号包住) | 用了 cmd 的 `-d "{\"title\":...}"`:PowerShell 不认 `\"`,JSON 里的 `,` 又被当成数组分隔符,`-d` 只拿到半截 `{title:smoke` → `422`,剩下的碎片被 curl 当成额外 URL → 打印 `HTTP 422HTTP 000` |
| cmd.exe | `-d "{\"title\":\"smoke\"}"`(双引号包住) | 用了 PowerShell 的 `-d '...'`:cmd 不把 `'` 当引号,请求体里混进字面的 `'` → `422`「请求体不是合法的 JSON」 |

cmd.exe 还不认行尾的反引号续行:把上面那个多行 PowerShell 片段整段粘进 cmd(换行被吞掉)时,
那两个 `` ` `` 会被 curl 当成额外 URL,输出形如 `422`n000`n000`n`——其中 `` `n `` 只是被原样打印的字面量。

两种 shell 各自的一行写法(**必须写在一行**;另外别存成 `.bat`,`.bat` 里 `%{http_code}` 会被当成变量):

```powershell
# PowerShell
curl.exe -s -o NUL -w "HTTP %{http_code}" -X POST http://localhost:443/api/agent/events -H "Authorization: Bearer <令牌>" -H "Content-Type: application/json" -d '{\"title\":\"smoke\",\"start_at\":\"2026-11-03T14:00:00\",\"end_at\":\"2026-11-03T15:00:00\",\"client_ref\":\"smoke-1\"}'
```

```bat
rem cmd.exe
curl.exe -s -o NUL -w "HTTP %{http_code}" -X POST http://localhost:443/api/agent/events -H "Authorization: Bearer <令牌>" -H "Content-Type: application/json" -d "{\"title\":\"smoke\",\"start_at\":\"2026-11-03T14:00:00\",\"end_at\":\"2026-11-03T15:00:00\",\"client_ref\":\"smoke-1\"}"
```

这两种一行写法都只适合纯 ASCII 的字段值。带中文的标题、或者字段一多,就请走上面的 UTF-8 文件方式——
那是最不容易出错的一种,两种 shell 都能用。任何 422 先看响应体的 `error.message` 与 `error.fields`:
`message` 是「请求体不是合法的 JSON」说明 shell 把请求体改坏了,`fields` 才指向字段本身。

第 3 步之后的映射关系(同样是剥前缀 + 拼接):

| 对外地址 | 转发到后端 | 结果 |
|---|---|---|
| `/agent/events` | `/api/agent/events` | Agent 新建日程 |
| `/agent/events/{id}` | `/api/agent/events/{id}` | Agent 回查自己建的事件 |
| `/agent/admin` | `/api/agent/admin` | 404 |

```json
  "all_day": false, "timezone": "Australia/Brisbane",
  "start_at_utc": "2026-11-03T04:00:00Z", "start_local": "2026-11-03T14:00:00+10:00",
  "sequence": 0, "source": "agent", "client_ref": "dentist-2026-11-03",
  "reminders": [1440, 60], "reminder_labels": ["提前 1 天", "提前 1 小时"],
  "url": "https://example.com/clinic",
  "duplicate": false,
  "sync": { "ok": true, "changed": true, "version": 12, "mail_created": 2, "error": null }
}
```

| 状态码 | 含义 |
|---|---|
| `201` | 新建成功,ICS 已重新生成 |
| `200` + `"duplicate": true` | 该 `client_ref` 已存在,返回原事件;不会重复建、不会重新发信 |
| `401` | 缺少或错误令牌(令牌被停用或撤销后也算) |
| `404` | 两个来源都没有令牌(`.env` 为空且平台内没有启用的令牌),接口视为不存在 |
| `422` | 字段校验失败,`error.fields` 给出逐字段原因 |
| `429` | 超过 `AGENT_RATE_LIMIT_PER_MINUTE`(默认 60/分钟),带 `Retry-After` |

即使 `sync.ok` 为 `false`(ICS 生成失败),事件也已经安全落库,后台会每分钟自动修复;
Agent 可以用 `GET /agent/events/{id}` 回查。

#### 支持的字段

`title`(必填,≤200)、`start_at`/`end_at`(定时事件,ISO 8601)、
`start_date`/`end_date`(全天事件,`end_date` 不含当天)、`all_day`、
`timezone`(IANA 名 / 中文名 / **序号**,见下)、`location`(≤500)、`description`(≤10000)、
`url`(≤1000,备注链接 → ICS `URL`)、`reminders`(提醒,见下)、
`status`(`confirmed`/`tentative`/`cancelled`)、`rrule`(标准 RRULE)或
`recurrence`(每日/每周/每月/每年)+ `recurrence_until`、`client_ref`(幂等键,≤200)、
`duration_minutes`(1–10080,不给 `end_at` 时用它算结束时间)。

只能给 `start_at` 时,结束时间自动取 `duration_minutes`;再不给就用
`DEFAULT_EVENT_DURATION_MINUTES`(默认 60 分钟)。

`reminders` 是**提前分钟数**的列表,每条导出一个 ICS `VALARM`:

- JSON 写数组:`"reminders": [1440, 15, 0]`;
- 表单形态写逗号分隔字符串:`reminders=1440,15,0`(两种形态等价,会去重并从大到小排序);
- `0` = 事件开始时,正数 = 提前,负数 = 延后,绝对值上限 `43200`(30 天);
- 全天事件以当天 `00:00` 为基准,所以 `1440` = 提前 1 天;
- 非整数或越界会被拒绝(422),不会被静默忽略;单个事件最多 50 条提醒;
- 不提交该字段 = 保留原值,提交 `[]` = 清空提醒。

`start_at` 接受这些写法(不带偏移量时按 `timezone` 解释):

```text
2026-11-03T14:00:00        2026-11-03 14:00        2026-11-03T14:00
2026-11-03                 2026/11/03 14:00        2026年11月8日 14:00
2026-11-8 9:5              2026-11-03T04:00:00Z    2026-11-03T14:00:00+10:00
```

请求体既可以是 `application/json`,也可以是 `application/x-www-form-urlencoded`
(表单里留空的字段视为未提供)。

#### iOS 快捷指令

快捷指令的「获取 URL 内容」用 **Form** 请求体最省事——不用手写 JSON,也就不用处理转义。

在 iPhone 上新建快捷指令,加入以下操作:

| 操作 | 配置 |
|---|---|
| 获取 URL 内容 | URL:`https://sisi-laptop.tail921448.ts.net/agent/events` |
| | 展开「显示更多」→ 方法:`POST` |
| | 请求体:`Form` |
| | 头部:`Authorization` = `Bearer <你的令牌>`(平台内生成的或 `.env` 里的都行) |

Form 字段按下表填(不需要的字段直接不添加):

| 字段 | 值 |
|---|---|
| `title` | 文本,或用「询问输入」/「听写文本」的结果 |
| `start_at` | 日期变量,或先用「格式化日期」输出 `yyyy-MM-dd HH:mm` |
| `duration_minutes` | `60`(可省略,省略时用服务器默认时长) |
| `timezone` | 可省略:省略时用服务器 `DEFAULT_TIMEZONE`(本部署即 `Australia/Brisbane`)。要显式写就填 IANA 名、**序号**(如 `1`)或中文名(如「北京时间」),**不能填偏移量**——见下方「timezone 怎么填」 |
| `location` | 可选 |
| `reminders` | 可选;填 `15` 或 `1440,15`,`0` 表示事件开始时(相对事件开始时间) |
| `url` | 可选;备注链接,如会议地址 |
| `client_ref` | 可选;填一个每次唯一的值(如「提供输入」的 UUID),重试就不会重复建 |

一个「说一句话加日程」的流程示例:

```text
听写文本                        → 得到标题
询问输入(类型:日期与时间)      → 得到开始时间
格式化日期(自定义 yyyy-MM-dd HH:mm)→ 得到 start_at
获取 URL 内容(POST / Form,头部带令牌)
获取词典值(duplicate)           → 判断是否重复
显示通知                        → “已添加”或“已存在”
```

注意事项:

- iPhone 必须连着 Tailscale 才能访问该地址。
- 令牌会保存在快捷指令里。如果要分享这个快捷指令,请在**设置 → 远程接入令牌**里
  为对方单独生成一枚(用完直接撤销),不要把自己的令牌给别人。
- 快捷指令把「日期」变量直接塞进 Form 字段时,格式取决于系统语言设置;
  用「格式化日期」显式指定 `yyyy-MM-dd HH:mm` 最稳妥。
- 服务端返回 `201` 表示新建成功、`200` 且 `duplicate: true` 表示这次是重复提交。
  可以用「获取词典值」读取 `sync.ok` 确认 ICS 是否已同步。

#### 提醒怎么填(reminders)

`reminders` 是**提前分钟数**,不是时刻,所以不用管时区,也不用管夏令时:

| 值 | 含义 |
|---|---|
| `0` | 事件开始时 |
| `15` | 提前 15 分钟 |
| `60` | 提前 1 小时 |
| `1440` | 提前 1 天 |
| `10080` | 提前 1 周 |
| `-10` | **延后** 10 分钟(事件开始之后) |

- **多条**用逗号分隔:`reminders` = `15,1440`;贴 JSON 数组 `[15,1440]` 也接受。
  顺序与重复都无所谓——入库时会去重并从大到小排序(顺序不能影响导出内容哈希)。
- **上限**:一个事件最多 50 条;单条绝对值不超过 `43200` 分钟(30 天)。
  越界、拼错(如 `15,abc`)或把秒当分钟写都会返回 `422`,提示
  「提醒只能是整数分钟数,多个值用逗号分隔(如 15,1440)……」。空值 = 不提醒,不报错。
- **全天事件**没有时刻,基准是当天 `00:00`:所以 `1440` 等于**前一天零点**
  (与 iCloud 语义一致),而不是「前一天的同一时刻」。
- **导出形态**:每条提醒一个 `VALARM`(`ACTION:DISPLAY` + `DESCRIPTION:标题` +
  `TRIGGER:-PT15M`)。相对时长由订阅端按各实例的开始时刻计算,所以重复事件与跨时区事件
  都不需要逐实例换算。
- **改已有的日程**:`/api/agent` 只有新建与回读,提醒要在电脑端表单里改;
  `PATCH /api/v1/events` 的语义是「不传 = 保留原值,传 `[]` = 清空」。

> **能不能真的弹出来,取决于订阅端。** iPhone 的**订阅(只读)日历**由本机
> 「设置 → 日历 → 默认提醒时间」决定,系统**不保证**逐条响应订阅源里的 `VALARM`。
> 若目标是「到点一定提醒」,需要在真机上确认两条路径的实际表现:① 订阅只读日历 +
> 系统默认提醒时间;② 把 `calendar.ics`(或邮件附件)导入系统日历(这条路径会走
> 文件里的 `VALARM`)。导出侧只负责把 `VALARM` 写正确。
> 这条待办记录在 `todo.md` 的「提醒相关的后续」。

#### timezone 怎么填

`timezone` 认三种写法:**IANA 名**(`Australia/Brisbane`)、**中文名**(`北京时间`)、
以及 `/admin/settings` 默认时区下拉框里的**序号**(`1` = 北京时间、`11` = 悉尼时间)。
偏移量与缩写(`+10:00`、`AEST`、`GMT+10`)仍会被拒:返回 `422`,`fields.timezone` 提示
「未识别的时区:…可填 IANA 名…也可填设置页列出的序号 1-30…」。

序号表固定不变(只会在末尾追加),完整清单见
[`docs/static/app-timezones.md`](static/app-timezones.md);也可以直接读接口:

```powershell
curl.exe -s http://localhost:443/api/v1/settings -H "Cookie: <登录后的会话>"
# → {"timezone_choices": [{"index": 1, "iana": "Asia/Shanghai", "label": "北京时间", ...}, ...]}
```

麻烦的地方在于:**快捷指令没有能取到设备 IANA 名的动作**。「转换时区」只认它自带的城市列表,
既拿不到当前时区的名字,也不接受用文本传进去的名字(见
[Apple Shortcuts and Time Zones](https://joe-steel.com/2025-03-31-Apple-Shortcuts-and-Time-Zones.html))。
序号就是为此准备的:在设置页看到「1. 北京时间」,快捷指令里填 `1` 即可。可行写法:

| 写法 | 表单字段 | 说明 |
|---|---|---|
| 不填(**推荐**) | 不添加 `timezone` | 服务端用 `DEFAULT_TIMEZONE`,本部署就是 `Australia/Brisbane` |
| 写死序号 | `timezone` = `1`(用「文本」动作,北京) | 最短、最不容易打错;序号含义见设置页下拉框 |
| 写死 IANA 名 | `timezone` = `Australia/Brisbane` | 与上一条等价,只是把意图显式写在快捷指令里 |
| 跟随手机当前时区 | `start_at` 用「格式化日期」输出**带偏移量**的时间(内置 `ISO 8601`,或自定义 `yyyy-MM-dd'T'HH:mm:ssZZZZZ`),`timezone` 仍填 `Australia/Brisbane` | 时刻由手机的偏移量决定;日历里仍按 `Australia/Brisbane` 还原显示 |

服务端如何解释时间(实测,`DEFAULT_TIMEZONE=Australia/Brisbane`):

| 提交 | 落库时刻 | 日历里显示为 |
|---|---|---|
| `start_at=2026-11-03T14:00:00` + `timezone=Australia/Brisbane`(或省略 `timezone`) | `2026-11-03T04:00:00Z` | 11-03 14:00(+10:00) |
| `start_at=2026-11-03T14:00:00+11:00` + `timezone=Australia/Brisbane` | `2026-11-03T03:00:00Z` | 11-03 **13:00**(+10:00) |
| `start_at=2026-11-03T14:00:00Z` | `2026-11-03T14:00:00Z` | 11-04 **00:00**(+10:00) |

两条规则:**带偏移量(或 `Z`)按该偏移量解释,不带偏移量按 `timezone` 解释**;而事件存下来的
`timezone` 决定它在日历和 ICS 里怎么显示。所以:

- 想要「永远是布里斯班时间 14:00 的日程」→ 发**不带偏移量**的本地时间(前两种写法)。
- 想要「此刻手机所在地的 14:00」→ 才发带偏移量的时间;注意它在日历里会换算成布里斯班时间。
- **不要**发 `...Z`——那是 UTC 语义,会被当成 14:00 世界时,在布里斯班直接跳到次日 0 点。

## 4. 数据与备份

`/data`(主机 `./data`)是唯一需要持久化和备份的应用数据目录:

```text
data/
├─ calendar.db          # SQLite 主库(WAL 模式)
├─ calendar.db-wal      # WAL 日志
├─ calendar.db-shm      # 共享内存索引
├─ admin.hash           # 管理员口令哈希(权限已收紧)
├─ session_secret       # 会话签名密钥
├─ export/
│  ├─ calendar.ics      # 全库并集:内部一致性产物,可随时重建(不再对外暴露)
│  └─ feeds/            # 按订阅目标发布的文件,经 /calendar/<令牌>.ics 对外
│     ├─ user-<id>.ics  # 某个账号可见的范围(个人 + 它能看到的共享日历)
│     └─ family.ics     # 家庭共享日历范围(令牌 user_id 为空时用这一个)
├─ snapshots/           # 导出版本快照,供邮件重试使用
│  ├─ calendar-v{N}-<key>.ics           # 完整版本快照(不可变)
│  └─ calendar-v{N}-<key>-upcoming.ics  # 邮件附件专用:该目标里尚未结束的日程
└─ backups/             # 命令行生成的备份
```

其中 `<key>` 是订阅目标:账号目标为 `user-<账号id>`,`family` 为家庭共享范围。

备份与恢复**仍然只需 `data/` 整个目录**:上面这些都是同一份数据的派生文件,不需要单独备份
(见 4.3)。

### 4.1 手动备份(推荐方式)

使用 SQLite 在线备份 API,生成一致快照,不会拷到写了一半的 WAL:

```powershell
docker compose exec calendar python -m app.cli backup
docker compose exec calendar python -m app.cli backups
```

备份同时会按 `BACKUP_RETENTION_DAYS`(默认 14 天)清理过期文件。

> **2026-10-11 实测的坑**:容器**正在运行时**,第二个进程(任何 `docker compose exec ... app.cli ...`)
> 有可能打不开库,报 `sqlite3.OperationalError: unable to open database file`——这是 SQLite 在
> Windows 绑定挂载上的加锁限制,不是应用故障(应用自身读写正常、`/readyz` 正常)。
> 遇到时按下面的优先顺序处理:
>
> 1. 稍等几秒重试一次(锁竞争是间歇性的);
> 2. 需要做**一致性检查或恢复**这类重活时,先 `docker compose stop`,再
>    `docker compose run --rm calendar python -m app.cli verify`(单实例、无竞争);
> 3. 只想确认服务健康,用 `http://localhost:443/readyz` 与 **同步状态**页面(它们走应用自己的连接)。

> **在宿主机(不是容器)里跑 CLI 时,必须显式指定盘符路径**:`.env` 里的 `DATA_DIR=/data`
> 是给容器用的,Windows 上会被解析成当前盘符根目录下的 `\data`(例如 `D:\data`),
> 于是命令会操作另一个(可能是空的)库——备份看起来成功,备的却不是线上那份。
>
> ```powershell
> $env:DATA_DIR = "D:\桌面\sisi_apps\SisiCalendar\data"
> uv run python -m app.cli backups
> ```
>
> CLI 现在会自检:当仓库里有 `./data/calendar.db` 而本次 `DATA_DIR` 指向别处时,启动就打印
> `WARNING 本次操作的数据库是 …`,看到这条警告就先把 `DATA_DIR` 设对。

### 4.2 每天自动备份

后台任务每天会尝试清理过期备份。若需要自动**生成**备份,用 Windows 计划任务:

```powershell
schtasks /create /tn "SisiCalendar Backup" /sc daily /st 03:00 /tr ^
  "cmd /c cd /d D:\桌面\sisi_apps\SisiCalendar && docker compose exec -T calendar python -m app.cli backup"
```

Linux/NAS 可在系统的计划任务或 `cron` 中每天执行:

```bash
cd /volume1/docker/sisi-calendar && \
  docker compose exec -T calendar python -m app.cli backup
```

定时任务使用的账号必须有权限访问 Docker;命令里的目录必须是实际的 Compose 项目目录。

### 4.3 备份哪些东西

| 对象 | 是否必须 | 说明 |
|---|---|---|
| `calendar.db` | 必须 | 日程数据的唯一事实来源;运行中只备份 `app.cli backup` 生成的一致快照 |
| `admin.hash` | 按配置 | 没有从 `.env` 注入管理员哈希时必须保留 |
| `session_secret` | **必须** | 丢失/轮换会让会话、所有账号固定订阅地址与未使用验证码同时失效 |
| `.env` | 必须,但**单独保存** | 含 SMTP 口令,不能和普通数据压缩包混放 |
| 升级前离线留档 | 建议 | 先停服务,再复制整个 `data/`;不得在容器运行时单独复制 WAL 模式的 `calendar.db` |
| `export/calendar.ics` | 不需要 | 全库并集,可由数据库重新生成,可留作诊断 |
| `export/feeds/` | 不需要 | 各订阅目标的发布文件,可由数据库重新生成 |
| `snapshots/` | 不需要 | 仅用于邮件重试,过期会被清理 |

### 4.4 恢复流程

```powershell
# 1. 停止服务(必须,恢复期间不能有活动连接)
docker compose stop

# 2. 恢复(会先把当前库另存为 calendar.db.pre-restore)
docker compose run --rm calendar python -m app.cli restore /data/backups/calendar-20260101-030000.db

# 3. 启动并检查
docker compose up -d
docker compose exec calendar python -m app.cli verify
curl.exe -i http://localhost:443/readyz
```

`restore` 会一并清除 `-wal`/`-shm`,强制重新生成 ICS 并做一致性检查。
最后在 iPhone 上确认订阅内容已更新。

### 4.5 回退

如果恢复结果不对,把 `calendar.db.pre-restore` 改回 `calendar.db` 再重复上面的启动步骤即可。

## 5. 升级与回滚

### 5.1 升级

```powershell
# 1. 先备份
docker compose exec calendar python -m app.cli backup

# 2. 拉取新版本,对照 .env.example 复核新增/删除的配置项
git pull                      # 或替换代码目录
notepad .env

# 从旧版升级到 2026-10-12 版时必须:
#   删除 SUBSCRIPTION_URL
#   新增 PUBLIC_BASE_URL=https://<实际对外主机>/calendar
#   复核 EMAIL_CODE_TTL_SECONDS / EMAIL_CODE_MAX_ATTEMPTS / EMAIL_CODE_RESEND_SECONDS

# 3. 构建并重建容器
docker compose build
docker compose up -d --force-recreate

# 4. 迁移会自动执行,确认健康状态
docker compose ps
curl.exe -i http://localhost:443/readyz
```

NAS/Linux 用文本编辑器修改 `.env`,健康检查地址按实际映射端口调整。
`PUBLIC_BASE_URL` 必须显式写成当前部署的正式地址;不要依赖代码里的示例默认域名,
否则邀请邮件、页面和订阅邮件会生成错误的绝对地址。

### 5.2 回滚

```powershell
docker compose down
git checkout <上一个可用版本>
docker compose build
docker compose up -d
# 若新版本改过表结构,再执行一次恢复
docker compose stop
docker compose run --rm calendar python -m app.cli restore /data/backups/<升级前备份>.db
docker compose up -d
```

### 5.3 从单用户版升级到家庭版(2026-10-08)

单用户版升级到家庭版时,日程数据不用导出重灌。旧的无令牌订阅地址已取消;
原有两位测试用户均已手动换成账号固定地址,因此本轮只校验固定地址可用,不再做额外迁移:

```powershell
# 1. 先备份(升级前一定要有还原点)
docker compose exec calendar python -m app.cli backup
#    如需整目录离线留档,必须先停服务,否则单独复制 WAL 模式的 calendar.db 可能丢数据
docker compose stop
```

### 8.1 升级后容器反复重启 / `MultipleResultsFound`(2026-10-11 真机发现并修复)

**症状**:升级后第一次启动正常,从第二次启动起容器进入重启循环。`docker inspect` 显示
`exit=3`、状态 `Restarting`;日志里的调用链是

```text
app/main.py:87 lifespan -> app/bootstrap.py:176 startup_checks
  -> app/bootstrap.py:131 ensure_family_setup -> app/accounts.py sync_user_recipient
sqlalchemy.exc.MultipleResultsFound: Multiple rows were found when one or none was required
```

**根因**:第一次升级的 `ensure_family_setup` 把**每一个**历史外部收件人都写成
`sync_recipients.user_id = 首位管理员`,于是同一个账号名下出现两行。而 `user_id` 在代码里是
「账号收件人」的**身份标记**(每个账号只能一行),`sync_user_recipient()` 当时用
`scalar_one_or_none()` 取行,第二次启动必抛。

**修复**:

| 位置 | 改动 |
|---|---|
| `migrations/versions/0006_recipient_scope.py` | 新增 `scope_user_id` 列,把「身份」(`user_id`)与「范围」(`scope_user_id`)拆开;数据步骤把账号收件人的 `scope_user_id` 回填为 `user_id`,并修复已有重复绑定(同一 `user_id` 多行时只保留邮箱与该账号 `users.email` 一致的那行,其余改成 `scope_user_id = 该账号`、`user_id = NULL`;账号本身没有邮箱则全部降级) |
| `app/bootstrap.py` | 首次升级只写 `scope_user_id`,不写 `user_id`(`user_id` 保持为空) |
| `app/accounts.py` | `recipient_scope_user_id()` 改为 `scope_user_id or user_id or None`;`sync_user_recipient()` 不再用 `scalar_one_or_none`,多行时告警并按邮箱匹配选行、绝不误删;`delete_user` 会把「范围挂在该账号上且没有 `user_id`」的行退回家庭共享范围 |
| `app/mailqueue.py` | 邮件附件目标键改按 `recipient_scope_user_id()` 取 |
| `app/routers/api_recipients.py`、`templates/partials/recipients.html` | `scope` 扩为 `account`/`member`/`family` 三种,新增 `scope_user_id`/`scope_user_name`;收件人页面「范围」列显示「沿用某成员的可见日历(历史绑定)」 |
| `tests/test_family_upgrade_recipients.py`(新增 4 项)、`tests/test_family_mail.py::test_legacy_external_recipient_keeps_owner_scope_attachment`(新增)、`tests/test_family_accounts.py::test_legacy_recipients_keep_owner_scope_on_first_upgrade`(改为断言 `scope_user_id`) | 回归覆盖 |

**部署后实测**:迁移 `0005_family_accounts -> 0006_recipient_scope` 成功;两个历史收件人现在都是
`user_id = NULL`、`scope_user_id = 首位管理员`(收信范围与升级前一致),`user_id` 重复行计数为 0;
**连续重启两次均 `Up (healthy)` 且 `RestartCount=0`**;`app.cli verify` 一致;容器内
`/admin/partials/recipients` 200 且出现「沿用admin的可见日历」,`/api/v1/sync-recipients` 返回
`scope: member` 与「家庭管理员可见日历(历史绑定)」;`/admin`、`/admin/me`、`/admin/members`、
`/api/v1/calendars`、`/admin/partials/me` 都是 200;对外 `/calendar` 仍 200。
(2026-10-11 晚起无令牌的 `/calendar` 已取消,现在返回 404;本节其余内容为当日实测存档。)

**教训**:自动化测试没能拦住它。测试库是 `Base.metadata.create_all` 建出来的(`0006` 的修复函数
只能靠单独调用才能覆盖),而且回归用例当时只放了**一个**历史收件人,碰不到「多行同账号」这条路径;
只有真机升级(库里有两个历史收件人)才会暴露。**迁移里的数据修复逻辑与「多行」边界必须单独写用例**,
不能只靠 `create_all` + 单行夹具。

### 8.1.1 成员收不到共享日历的同步邮件(2026-10-13 真机发现并修复)

**症状**:共享日历里改了日程,只有「设置」页里的外部邮箱收到邮件,**成员的账号邮箱一封都没有**。

**根因**:账号收件人虽然是 `users.email` 的派生结果,却是一行**可以被删掉/停用的普通记录**:

1. 设置页的收件人「停用」(toggle)与「移除」(delete)两个路由**没有账号行守卫**
   ——只有 `/api/v1/sync-recipients` 拦了改名与删除,所以管理员在页面上点一下就能把成员的
   账号收件人删掉;
2. 删掉之后**没有任何路径把它补回来**。引导里的 `sync_user_recipient` 每次都跑,但结尾的
   `session.commit()` 只在 `changed` 为真时执行,而账号收件人的修复**不会**置 `changed`,
   所以那次修复只留在内存里,事务结束时被丢掉。

真机现场:两位成员的邮箱都早已验证通过,`sync_recipients` 里却只剩一行。

**修复**:

| 位置 | 改动 |
|---|---|
| `app/accounts.py` | 新增 `sync_account_recipients()`:把全部账号对齐成收件人记录(启用 + 已验证 → 一条**启用**的账号收件人;账号停用 → 该行 `enabled=False` 但**不删行**),返回变化行数;`sync_user_recipient()` 补上「账号启用时把该行恢复成启用」 |
| `app/bootstrap.py` | 改用 `sync_account_recipients()`,结尾**无条件 `session.commit()`**(漏标的修复不允许只留在内存里) |
| `app/mailqueue.py` | `ensure_delivery_tasks()` 在**建发信任务之前**先对齐一次,不再依赖「上一次启动是否修好」 |
| `app/routers/pages.py` | 设置页与收件人片段渲染前同样对齐;新增 `_guard_external_recipient()`,`toggle`/`remove` 命中账号行返回 **409**;`_recipients()` 只返回外部行,账号邮箱改到下方**只读**列表 |
| `app/routers/api_recipients.py` | `PATCH {"enabled": …}` 命中账号行同样 **409**(此前只拦改名/删除) |
| `app/sync_service.py`、`app/mailqueue.py` | 新增 `changed_calendar_ids` 与 `_scope_calendar_ids()`:**一次改动只通知「可见范围包含这条日历」的收件人**(换日历传新旧两条;手动群发/CLI/后台修复不传 = 全员) |
| `app/routers/api_events.py` | 三个写路由把改动的日历交给 `publish`;**顺带修正「先搬家再校验乐观锁」的顺序缺陷**(搬家会刷新 `updated_at`,带 `expected_updated_at` 的换日历请求此前必然 409) |

**部署后实测(2026-10-13)**:重建镜像 → 迁移 `0007 → 0008` 成功、启动无 `Traceback`;
`sync_recipients` 从 1 行变成 2 行(那位成员的账号收件人被自动建出并提交,两行都 `enabled=1`);
在容器里对**在线库**跑回滚事务探针:共享日历变动 → 通知 2 人、管理员私人日历变动 → 0 人、
不带筛选 → 2 人。详见《验收测试记录》§3.8。

**教训**:「派生数据」不能做成**可被用户删掉、但又没有重建路径**的行。要么让它彻底派生
(每次用之前重算),要么就必须保证**每个删除入口都有守卫、每个写入路径都会重建**。
这次两个都漏了:页面删除路径没有守卫,重建路径又因为 `changed` 标记不准确而没有提交。
**凡是「修复逻辑依赖 `changed` 标记才会提交」的地方,都要问一句:这个修复会置 `changed` 吗?**

### 8.2 `SESSION_SECRET` 加固与副作用(2026-10-11,含固定订阅地址)

> **2026-10-11 补充**:从固定订阅地址上线起,`data/session_secret` 不只是会话签名密钥,
> 还是**订阅地址与邮箱验证码的派生密钥**。手动轮换/清空它会让
> **每个账号的固定订阅地址同时失效**(订阅端立刻变成 404)并作废所有未使用的验证码,
> 需要给每台设备重新填一次新地址。没有明确理由不要动这个文件。

界面开放给 tailnet 之后,会话签名密钥的口令强度就成了必须处理的问题:`.env` 里的
`SESSION_SECRET` 原本只有 5 个字符,而且它**盖住了** `data/session_secret` 里那份 64 字符的随机密钥。
已把 `.env` 中该行清空,改为使用文件里的强密钥。会话 Cookie 由该密钥签名,过短的密钥意味着
理论上可被枚举伪造,因此这不是可选项。

- **副作用**:已登录的浏览器需要重新登录;所有账号的**固定订阅地址**变化,
  需要在每台订阅设备上替换;所有未使用的邮箱验证码作废;
- **不影响**:数据库中的日程、邮件队列,以及独立随机生成的临时/家庭订阅令牌;
- 口径与 §2.1 一致:`.env` 的 `SESSION_SECRET` 留空即使用 `data/session_secret` 里那份自动生成的
  64 字符随机密钥;把短密钥写回 `.env` 会再次盖住它。日常升级不得删除或轮换
  `data/session_secret`;备份恢复时必须连同原密钥一起恢复。

### 8.5 家人的订阅地址失效 / 旧地址 404(2026-10-11)

| 现象 | 原因 | 处理 |
|---|---|---|
| iPhone 上原有订阅显示「无法连接到账户」,`https://<节点>/calendar` 返回 404 纯文本 | 无令牌的旧地址**已被取消**(本轮需求明确只保留令牌版地址) | 让本人登录 `/calendar/admin/me`,复制「账号订阅地址(固定)」那条完整地址,在手机上删掉旧订阅、用新地址重新添加 |
| 某条**临时/家庭**地址突然 404,但库里记录还在 | 该随机令牌被停用或撤销(面板里有开关) | 停用的重新启用;撤销的只能重建一条(明文无法找回);账号固定地址不允许停用/撤销 |

| 页面上看不到固定地址那一行 | 账号是引导之前建的、且启动时 `ensure_family_setup` 未跑完 | 重启容器(引导幂等),再看容器日志里 `公开面挂载前缀:/calendar` 之后的引导结果 |

排查用的只读命令(容器内,不会改数据):

```bash
from app.db import get_session_factory
from app.models import FeedToken, User
s = get_session_factory()()
for u in s.query(User).all():
    print(u.username, u.email, u.email_verified_at)

PY
```

### 8.6 收不到验证码邮件(2026-10-11)

新注册与改邮箱都会发一封 6 位验证码邮件,规则:30 分钟有效、最多错 5 次、重发冷却 60 秒。

| 现象 | 原因 | 处理 |
|---|---|---|
| 注册后页面提示「验证码邮件发送失败」 | SMTP 未配置或连接失败(设置页「SMTP 发信配置」显示未配置/测试失败) | 先在 `/admin/sync` 或设置页修好 SMTP,再到验证页点「重新发送验证码」 |
| 邮件收不到但发送成功 | 进了垃圾箱;或收件人把发件人当成了推广 | 让对方查垃圾箱/白名单 |
| 提示「验证码不正确」5 次后只能重发 | 第 5 次错误会把验证码作废(防爆破) | 点「重新发送验证码」,等冷却结束后收新码 |
| 提示「还没有可用的验证码」 | 从未发过、或验证码已被作废 | 点「重新发送验证码」 |
| 家人邮箱填错了 | 账号本身还没验证,允许在验证页直接改 | 在 `/calendar/verify-email` 的「改邮箱」里填对的地址,系统会立刻给新地址发码 |

验证码在库里只有 HMAC 哈希,日志与审计里也不会出现;排障时**不要**要求家人把验证码发给你,
让他们自己在页面上填即可。

## 9. 家庭版数据与权限速查(2026-10-08 新增)

### 9.1 数据模型(迁移 `0005_family_accounts` + `0006_recipient_scope` + `0008_delivery_actor`)

| 表 | 关键列与语义 |
|---|---|
| `users` | `username` 唯一登录名;`display_name`;`email`(可选,**账号收件人地址**,应用层保证不与其他账号重复);`color`;`timezone`(可空 = 跟随应用默认时区);`role`(`admin` / `member`);`enabled`;`must_change_password`;`password_hash`(Argon2id);`last_login_at`;迁移 `0007` 新增 `email_verified_at`、`email_verify_code_hash`(只存 HMAC)、`email_verify_expires_at`、`email_verify_attempts`、`email_verify_sent_at` |
| `calendars` | `kind`(`personal` 私人 / `shared` 共享);`owner_user_id`(私人日历 = 归属账号,共享日历为 `NULL`);`name`;`color`;`sort_order` |
| `calendar_members` | `(calendar_id, user_id)` 唯一;`role` = `owner` / `editor` / `viewer` |
| `invite_codes` | 只存 `sha256`;`label`;`max_uses`(默认 1,上限 20);`used_count`;`enabled`;`expires_at`;`created_by_user_id` |
| `feed_tokens` | 只存 `sha256`;`user_id` 为 `NULL` 表示**家庭共享范围**;`label`;`enabled`;`last_used_at`。每个账号有一条 `label = '账号订阅地址(固定)'` 的行:明文由 `session_secret` 派生(可重算,所以能长期显示),界面上不可停用/撤销 |
| `events` | 新增 `calendar_id`(FK `calendars.id`,`ON DELETE SET NULL`,索引 `ix_events_calendar_id`)与 `created_by_user_id`;新增复合索引 `ix_events_calendar_start`(`calendar_id`, `deleted_at`, `start_at_utc`) |
| `sync_recipients` | `user_id` = **身份**(非空 = 账号收件人,由 `users.email` 派生,**每个账号只能一行**;`NULL` = 外部邮箱);`scope_user_id` = **收信范围**(迁移 `0006_recipient_scope` 新增,带索引):附件按它的可见日历裁剪,为空 = 家庭共享日历 |
| `mail_deliveries` | 发信任务,幂等键 `(export_version, recipient_id)`;迁移 `0008_delivery_actor` 新增 `actor_user_id`(发起人账号,**无外键**,删账号时由应用层显式置空)与 `actor_label`(显示名快照,账号删除后仍能说明当时是谁) |
| `agent_tokens` | 新增 `user_id`(令牌归属)与 `calendar_id`(默认落库日历) |

`sync_recipients` 两列的分工:`user_id` 决定「这行是谁的账号收件人」,`scope_user_id` 决定
「发给这个邮箱的附件按谁的可见范围裁剪」。历史外部邮箱(单用户版升级上来的)只写
`scope_user_id`、不写 `user_id`,所以账号名下永远只有一行;取值统一走
`app/accounts.py::recipient_scope_user_id()`,顺序是 `scope_user_id or user_id or None`。
迁移 `0006_recipient_scope` 还会修复已有重复绑定(同一 `user_id` 多行时只保留邮箱与该账号
`users.email` 一致的那行,其余改成 `scope_user_id = 该账号`、`user_id = NULL`;账号没有邮箱时
全部降级)——背景见 §8.1。

时间仍然一律以 **naive UTC** 落库;原有不变量(UID 稳定、发布文件原子替换、导出内容确定性、
邮件幂等键 `(export_version, recipient_id)`、SMTP 口令只来自环境变量)全部不变。

### 9.2 权限矩阵(隐私第一)

| 对象 | 谁能读 | 谁能写 |
|---|---|---|
| 私人日历 | **只有归属账号**(管理员也读不到;按 id 读返回 404,列表里根本不出现) | 只有归属账号(别人写返回 403) |
| 共享日历 | 全体成员 | `owner`(家长 / 管理员)与 `editor`;新成员默认 `viewer` 只读 |

- 只有**管理员**能新建共享日历、调整成员在共享日历里的角色;
- 管理员的额外职责:成员(停用 / 启用、重置口令、改角色、删除)、邀请码、应用设置、
  同步与手动发信、外部收件人;
- 管理员**不能停用或删除自己**,也**不能删掉最后一个管理员**(409)。

### 9.3 订阅与邮件范围

| 通道 | 内容 |
|---|---|
| `/calendar/<令牌>.ics`(账号令牌) | 该账号**可见**的日历:个人日历 + 它能看到的家庭共享日历 |
| `/calendar/<令牌>.ics`(固定令牌) | 同上;由服务端派生、永不变更,界面不可撤销 |
| `/calendar/<令牌>.ics`(家庭令牌,`user_id` 为空) | **只含家庭共享日历**,适合公用设备 |
| `/calendar`、`/calendar.ics`(旧地址) | **已取消**:404 纯文本,不再提供任何日历 |
| 账号收件人(账号邮箱,`user_id` 非空) | 自己可见日历里**尚未结束**的日程 |
| 历史绑定的外部邮箱(`scope_user_id` 非空、`user_id` 为空) | **被绑定账号的可见范围**里尚未结束的日程 —— 与升级前的收信范围等价(单用户版时它收到的是当时那份完整日历) |
| 外部邮箱收件人(两列都为空) | **只有家庭共享日历**范围 |

**什么时候发**(2026-10-12 第四轮):具体日程的增删改**只通知「可见范围包含这次改动的日历」的
收件人**(换日历的事件新旧两边都通知);看不见这条日程的人不会收到一封附件里没有它的邮件。
手动群发(「重新生成 ICS」「向当前人员发送最新版」)、CLI 导出与后台修复拿不到具体日历,
仍然发给全部启用的收件人。

**谁来维护**:账号收件人由账号资料派生(`sync_account_recipients` 在启动、发信前与设置页渲染前
对齐;成员邮箱**验证通过**即自动成为收件人,停用账号即停掉),设置页与
`/api/v1/sync-recipients` **只维护外部邮箱**,对账号行的改名/启停/删除一律 `409`。

任何人的私人日程都不会进入别人的邮件。邮件正文里**不再出现并集订阅地址**:
账号收件人收到的是**他自己**那条固定地址(便于直接复制到 iPhone),外部邮箱一条都不给。

随机令牌只存哈希,明文只在生成那一次显示,停用或撤销后地址**立刻 404**;
账号固定地址的明文可由服务端重新算出,所以页面长期可见,但库里同样只有哈希。
版本号与内容哈希仍由**全库并集**(内部产物 `export/calendar.ics`)决定,
所以任何成员的任何改动都会推进全局 `export_version`。

### 9.4 邮箱验证速查(2026-10-11 新增,迁移 `0007_email_verification`)

| 项 | 规则 |
|---|---|
| 谁能被挡 | **非管理员**账号,只要有邮箱且 `email_verified_at IS NULL`,进任何业务页面/接口都会被挡(页面 303 → `/calendar/verify-email`,`/api` 403 `email_not_verified`) |
| 谁能豁免 | 首位管理员(救急用);**没有邮箱**的成员不挡,只在「我的设置」里被提示去补邮箱 |
| 注册 | 必须填邮箱;提交后立刻发验证码,并跳到验证页 |
| 验证码 | 6 位数字,30 分钟有效(`EMAIL_CODE_TTL_SECONDS`),最多错 5 次(`EMAIL_CODE_MAX_ATTEMPTS`,第 5 次作废),重发冷却 60 秒(`EMAIL_CODE_RESEND_SECONDS`) |
| 改邮箱 | 资料页里邮箱一旦真的变了:立刻回到待验证状态、作废旧码、给新地址发新码;验证页也能直接改(填错邮箱的补救) |
| 验证通过 | 标记 `email_verified_at`,补建账号收件人(未验证前**不发**日程邮件),并补发一封「你的固定订阅地址」邮件 |
| 存储 | 库里只有 `HMAC(session_secret, "verify:<账号id>:<验证码>")` 与过期时间/次数/上次发送时间;验证码绝不进日志、审计或数据库明文 |
| 管理员找不到入口 | 管理员平时看不到验证页(不满足条件时会被送回 `/admin`);想验证自己的邮箱,先确认它已经填进资料页 |

常用排查 SQL(容器内只读):

```bash
docker compose exec -T calendar python -c "from app.db import get_session_factory; from app.models import User; s=get_session_factory()(); [print(u.username, u.email, u.email_verified_at, u.email_verify_attempts, u.email_verify_expires_at) for u in s.query(User).all()]"
```

想把某个人的验证状态**手动重置**成「已验证」(例如邮件服务长期不可用时的应急):

```bash
docker compose exec -T calendar python -c "from app.db import get_session_factory; from app.models import User; from app.timeutil import utcnow; s=get_session_factory()(); u=s.query(User).filter(User.username=='sisi').one(); u.email_verified_at=utcnow(); u.email_verify_code_hash=None; s.commit(); print('ok', u.username)"
```

> 手动重置等于跳过归属确认:只在确认邮箱确实是本人时使用,并优先修好 SMTP(§8.6)。
