### 9. `/admin` 和事件 API 不能通过 Tailscale 地址访问

**状态**:部署验证通过。

- 实测(`/calendar/*` 前缀下全部 404,证明管理面未被转发):

  | 路径 | 结果 |
  |---|---|
  | `/calendar/admin` | 404 |
  | `/calendar/login` | 404 |
  | `/calendar/api/v1/events` | 404 |
  | `/calendar/readyz` | 404 |
  | `/calendar/healthz` | 404 |

- 实测:裸路径 `/admin`、`/login`、`/api/v1/*`、`/static/*` 在 Tailscale 地址上返回 401,
  内容均不含本服务的任何页面或数据——它们命中 `/` 路由,转发到另一台本机服务(DSH Web GUI),
  与 SisiCalendar 无关。
- **部署过程中发现并修复的真实缺陷**:Tailscale Serve 会剥掉挂载前缀。最初按设计文档的命令
  用 `--set-path=/calendar http://127.0.0.1:443` 配置后,`/calendar` 落到后端 `/`(管理首页的
  303 重定向),`/calendar/login` 返回 200(登录页),`/calendar/api/v1/events` 返回 401——
  **管理面暴露给了整个 tailnet**。把目标改为 `http://127.0.0.1:443/calendar` 后,
  后端路径变为 `/calendar` 且其余子路径一律 404,问题消除。
- 由于 Docker NAT 让本机请求与代理请求的来源地址相同(容器内均显示为 `172.19.0.1`),
  应用层无法区分二者,隔离**只能**由 Serve 的挂载路径保证。因此《部署与运维》第 3 节已修正
  命令并在文档中标注「目标必须带路径」及对应的 404 验证步骤。

### 部署过程中发现并修复的两个缺陷

1. **管理面经 Tailscale 暴露**(安全,已修复):Serve 剥前缀导致 `/calendar/admin` 转发到后端
   `/admin`,`/calendar/login` 实测返回 200。修复方式是把 Serve 目标改为
   `http://127.0.0.1:443/calendar`,并修正文档与 README 中的命令。详见第 9 条。

2. **导出内容不确定性导致重复发信**(正确性,已修复):`app/ics.py` 的 `DTSTAMP` 原本取
   挂钟时间(`utcnow()`),于是相隔一秒的两次导出会得到不同内容哈希。而导出器正是用内容哈希
   判断「是否需要新版本」,结果是没有改动的保存也会递增版本,并**向所有同步人员重发一次完整
   日历**。修复为取事件自身的 `updated_at`(与 `LAST-MODIFIED` 一致),新增回归测试
   `test_content_is_deterministic_across_wall_clock` 把时钟拨到第二天后断言字节完全一致。

   这个缺陷是被 `test_content_is_deterministic` 的偶发失败暴露出来的——它只在两次导出跨越
   秒边界时失败,属于典型的「测试偶发失败掩盖真实 bug」。修复后该测试不再依赖时序。

验证脚本覆盖:健康与就绪检查、订阅响应头与别名一致性、HEAD、未授权拒绝、登录与 CSRF、
中文事件创建与本地时间到 UTC 换算、ICS 结构与时区组件、ETag/Last-Modified 条件请求、
范围查询、同步状态字段、四个管理页面渲染、软删除后从订阅移除。

复现方式:

## 3.3 迭代记录(平台内管理远程接入令牌)

### 需求:允许用户在平台内添加并管理远程接入的 token

原状:令牌只能写在 `.env` 的 `AGENT_API_TOKEN` 里(逗号分隔多个),界面无法查看或撤销。

改动后:登录 → **设置 → 远程接入令牌** 可生成 / 改名 / 停用 / 启用 / 撤销。
`.env` 那一路**保留**,与库内令牌取并集鉴权,作为兜底与恢复通道。

### 关键设计决定(以及为什么)

| 决定 | 理由 |
|---|---|
| 库里只存 `sha256(token)`,明文只在创建时显示一次 | 与 `AGENTS.md` 第 6 条(口令只从环境注入)同级处理;数据库与备份泄漏不暴露令牌。令牌是高熵随机串,用快哈希即可,不必上 Argon2id |
| `.env` 令牌继续生效(并集) | 不破坏已有部署;数据库损坏时仍可应急 |
| 页面只显示指纹(`sha256` 前 16 位) | 与审计日志 `agent:<指纹>` 一一对应,能判断是哪枚令牌在建日程,又不泄露令牌 |
| 撤销是硬删除;停用保留记录 | 撤销后无需保留任何哈希;停用用于临时冻结 |
| 生成令牌必须勾选确认 | 与「同步人员」的隐私二次确认同构:该令牌可远程建日程并触发群发邮件 |
| 撤销最后一枚令牌后接口回到 404 | 与不变量 11 一致:一处令牌都没有时接口等同不存在 |

### 同轮事故与恢复记录(必读)

**事故**:部署时在**容器仍持有数据库**的情况下,从宿主机执行了 `uv run alembic upgrade head`。
`alembic.ini` 把 `sqlalchemy.url` 写死为 `./data/calendar.db`,所以这条命令直接打在真实库上;
两个进程(宿主机 alembic 与容器内应用)同时写同一个 SQLite 文件属于未定义行为,结果是一次
**撕裂的 schema 提交**:`sqlite_master` 里写入了 `agent_tokens` 及其索引(指向 rootpage 43–46),
而这几个页从未落到主文件(文件只有 42 页)。容器因此崩溃循环:

```text
sqlalchemy.exc.DatabaseError: (sqlite3.DatabaseError)
malformed database schema (agent_tokens) - invalid rootpage
```

**当时的处境**:`data/backups/` 是**空的**——此前从未生成过备份,没有可回滚的还原点。

**诊断**:普通连接连 `sqlite_master` 都读不了;用 `PRAGMA writable_schema=ON` 绕过 schema 解析后
读出全部 24 条 schema 记录与各表计数,确认**数据页完好**(77 事件 / 2 收件人 / 20 队列 / 版本 153),
坏的只是那 4 条指向不存在页的 schema 条目。

**恢复**(先在副本上验证流程,再对真实库执行):

1. 停容器,复制 `calendar.db` 留证;
2. `PRAGMA writable_schema=ON` → 删除 `agent_tokens`、`ix_agent_tokens_enabled`、
   `sqlite_autoindex_agent_tokens_1/2` 四条 schema 记录;
3. 把 `alembic_version` 退回 `0002_event_source`(让迁移重新建表,而不是手工造表);
4. `writable_schema=OFF` + `VACUUM` 重建文件 → `PRAGMA integrity_check` = `ok`;
5. 启动容器,由启动迁移在**单写者**环境下干净执行 `0002 → 0003`;
6. 立刻 `python -m app.cli backup` 建立首个真实还原点。

**无损证明**:把损坏快照(经 `writable_schema` 读取)与修复后的库逐表比对行数与内容哈希,
`events` / `sync_recipients` / `mail_deliveries` / `calendar_exports` / `calendar_export_state` /
`app_settings` / `alembic_version` **全部一致**(`DATA_IDENTICAL`)。
事故全程导出版本保持 153,未产生新版本、未发出任何邮件。

**教训(已写入 `AGENTS.md` 与 `todo.md`)**:

- `uv run alembic` **不读 `DATA_DIR`**,固定打在 `./data/calendar.db` 上;容器在跑时绝不能执行它。
  要在副本上试迁移,得另写一份临时 ini;
- 部署前应先停容器(或至少不要在容器运行时从宿主机改库);
- 备份不能依赖"需要时再手动做"——这次是运气好,坏在 schema 而不是数据页。
