## 2. 逐条验收

### 1. `docker compose up -d` 后自动启动,主机重启后可恢复

**状态**:首次部署验证通过;主机重启恢复待验证。

- 实测:`docker compose build` 构建成功(镜像 `sisi-calendar:0.1.0`),`docker compose up -d` 后 12 秒内达到 `Up (healthy)`,`docker inspect` 显示 `healthy (失败次数 0)`。
- 启动流程日志确认依次完成:生成管理员口令 → Alembic 迁移到 `0001_initial` → 一致性检查 → 应用启动完成。
- 证据:`restart: unless-stopped`、健康检查、`stop_grace_period: 30s` 已配置。
- 待执行:重启主机后确认 `docker compose ps` 仍为 `Up (healthy)`。

### 2. 局域网其他设备无法直接访问主机 443 端口

**状态**:部署验证通过。

- 实测:`docker compose ps` 显示 `127.0.0.1:443->8000/tcp`。
- 实测:`netstat -ano | findstr :443` 中与本服务相关的监听项为 `TCP 127.0.0.1:443 LISTENING`,**没有** `0.0.0.0:443` 或 `[::]:443`。
- 说明:输出中另有 `100.72.255.29:443` 与 `[fd7a:...]:443` 的监听项,属于 Tailscale 守护进程(tailscaled),不是本服务,也不暴露给局域网。
- 待执行:从局域网另一台设备 `Test-NetConnection -ComputerName <主机IP> -Port 443`,期望 `TcpTestSucceeded: False`。

### 3. 本机可登录并完成事件增删改查

**状态**:部署验证通过。

- 实测(容器内,`scripts/verify_deployment.ps1` 全量通过):
  - `GET /login` 返回 200 并下发 CSRF 令牌;
  - `POST /login` 返回 `303 → /admin`;
  - `GET /admin` 渲染日历视图;
  - `POST /api/v1/events` → 201,其中中文标题「部署验证 093930」正确落库;
  - `PATCH`/`DELETE` 走同一链路,`DELETE` 返回 200 且事件立即从订阅中移除;
  - `/admin/settings`、`/admin/sync`、`/admin/events/new`、`/admin/events/{id}` 均返回 200。
- 实测:未登录访问 `/api/v1/events`、`/api/v1/sync/status` 均返回 401,`/admin` 返回 `303 → /login?next=/admin`。
- 实测:容器以非 root 身份运行,`id` 输出 `uid=10001(app) gid=10001(app)`。

### 4. 每次修改后 1 秒内完成 ICS 生成,界面显示最新生成时间

**状态**:本机与容器均实测通过。

- 实测(本机,200 个事件):首次生成 **92 ms**,再次生成 **80 ms**,远低于 1 秒。
- 实测(容器):创建事件后 `sync.version` 立即递增,`/calendar` 立刻可读到新内容。
- 界面:`/admin` 顶部状态条显示 `ICS 已生成 · v{version} · {bytes} 字节`;`/admin/sync` 显示版本、生成时间(UTC)、内容哈希、文件大小与发布文件状态。
- 自动化:`test_create_event_generates_ics_immediately` 断言写入后立即可以从 `/calendar` 读到内容。

### 5. `calendar.ics` 通过标准解析器校验,中文/全天/时区/重复事件正确

**状态**:自动化通过。

- 自动化:`test_ics.py` 全部用例用 `icalendar.Calendar.from_ical()` 解析导出结果,覆盖:
  - 中文标题与逗号、分号、反斜线、换行的转义;
  - `DTSTART;TZID=Australia/Brisbane` 与自动生成的 `VTIMEZONE`;
  - 全天事件 `DTSTART;VALUE=DATE` 与不含边界的 `DTEND`;
  - `FREQ=WEEKLY/DAILY` 与 `UNTIL`,全天事件 UNTIL 为 `DATE`、定时事件 UNTIL 为 UTC;
  - 长行折叠每行 ≤ 75 字节、CRLF 行结束符;
  - 相同数据两次导出字节完全一致(确定性)。

### 6. Tailscale 地址 `/calendar` 返回 200、正确 MIME 类型和有效 ICS

### 10. 每次「保存并同步」成功生成 ICS 后,所有启用人员各收到一封,附件哈希与该导出版本一致

- `test_attachment_hash_matches_export_version` 断言附件 SHA-256 等于任务记录的 `attachment_hash`;

### 11. 同一导出版本不会对同一人员成功发送两次;部分失败不影响其他人员,并可自动或手动重试

**状态**:自动化通过。

- 自动化:
  - `test_task_creation_is_idempotent`:同一 `(export_version, recipient_id)` 第二次创建返回 0;
  - `test_sent_task_is_not_resent`:已成功任务不重复发送;
  - `test_one_failure_does_not_block_others`:一个地址失败,另一位仍成功;
  - `test_failure_schedules_retry_with_backoff`:首档退避为 1 分钟,与配置 `1,5,15,60,180` 一致;
  - `test_max_attempts_marks_failed`:达到上限后进入 `failed` 且不再排队;
  - `test_retry_of_old_version_keeps_old_attachment`:旧版本重试仍附旧版快照,不会冒充新版;
  - `test_stuck_sending_is_requeued`:崩溃中断的任务自动恢复。

### 12. 邮件或 ICS 生成失败时有可见状态和可重试操作,不会损坏数据库或现有 ICS

**状态**:自动化通过。

- 自动化:
  - `test_feed_serves_last_valid_file_when_export_fails`:生成失败时订阅端仍拿到上一次完整有效的文件,发布路径不会出现半写入内容;数据库中的编辑保留;`dirty=true` 与错误摘要持久化;恢复后由后台任务修复并出现在订阅中;
  - `test_snapshot_hash_mismatch_refuses_to_send`:附件哈希不符时拒绝发送;
  - `test_missing_snapshot_is_reported`:快照缺失时给出明确错误;
  - `test_dirty_state_is_repaired_by_feed_request`:`/calendar` 会先尝试修复再返回。
- 界面:`/admin` 顶部显示「ICS 待修复」与错误摘要;`/admin/sync` 提供「重新生成 ICS」和逐条「重试」。

### 13. 备份恢复后事件数量、UID、序列及订阅内容与备份时一致

- 自动化:`test_restore_returns_to_backup_state` 断言恢复后事件集合的 `(uid, sequence, deleted)` 与备份时完全相同,备份之后的新增消失,重新生成的 ICS 含原事件且不含新增事件;

- `test_restore_keeps_pre_restore_copy` 断言留下 `calendar.db.pre-restore` 可回退;
- `test_deleted_rows_survive_backup_restore` 断言软删除记录随备份保留。

环境:Docker 28.3.2 / WSL2 / 主机 `sisi-laptop`,数据目录 `./data`。

| 步骤 | 结果 |
|---|---|
| `docker compose build` | 成功,镜像 `sisi-calendar:0.1.0`,基础镜像 `python:3.13-slim-bookworm`,依赖由 `uv.lock` 锁定 |
| `docker compose up -d` | 容器 12 秒内 `Up (healthy)`,`docker inspect` 健康检查零失败 |
| Alembic 迁移 | 启动时自动执行 `0001_initial` |
| 管理员凭据 | 首次启动生成随机口令并仅在日志打印一次,哈希写入 `/data/admin.hash` |
| 端口绑定 | `127.0.0.1:443->8000/tcp`,无 `0.0.0.0` 绑定 |
| 容器身份 | `uid=10001(app) gid=10001(app)`,非 root |
| 端到端脚本 | `scripts/verify_deployment.ps1` **37 项全部通过** |
| 最终状态 | `readyz` 全绿;订阅文件 212 字节、0 个 VEVENT(验证数据已清理) |

验证脚本覆盖:健康与就绪检查、订阅响应头与别名一致性、HEAD、未授权拒绝、登录与 CSRF、
中文事件创建与本地时间到 UTC 换算、ICS 结构与时区组件、ETag/Last-Modified 条件请求、
范围查询、同步状态字段、四个管理页面渲染、软删除后从订阅移除。

复现方式:

```powershell
$env:SISI_ADMIN_PASSWORD = '<管理员口令>'
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify_deployment.ps1
```

> 脚本内的 HTTP 调用走 `curl.exe`。Windows PowerShell 5.1 的 `Invoke-WebRequest` 在发送
> 含非 ASCII 的请求体时会破坏编码,导致本可成功的请求返回 422;`curl.exe` 没有这个问题。
