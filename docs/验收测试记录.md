### 9. `/admin` 和事件 API 不能通过 Tailscale 地址访问(2026-10-11 起口径调整,**2026-10-12 再次收窄**)

**状态**:部署验证通过。**口径演进**:2026-10-11 曾把成员面按精确路径(`/login`、`/logout`、`/register`、`/admin`、`/api`、`/static`)直接开放给 tailnet;2026-10-12 起改为**对外只挂 `/calendar` 一段**,裸路径只在**本机**可用,判定标准是「对外只有一个前缀 + 管理操作需要登录与角色」。

- **2026-10-11 的旧口径(已作废)**:当时 `/calendar/*` 前缀下全是 404(证明订阅命名空间未被管理页污染),而裸路径 `/login`、`/register`、`/static/...` 返回 200、`/admin` 303、`/api/v1/calendars` 401。那张表**不再**是当前的暴露面判据。
- **2026-10-12 新口径**:同一个应用同时服务裸路径(本机 `http://localhost:443/...`)与
  `PUBLIC_BASE_URL` 的前缀入口(`https://<节点>/calendar/...`);对外只挂 `/calendar` 一段,
  成员入口变成 `/calendar/register`、`/calendar/login`、`/calendar/admin/...`、`/calendar/verify-email`。
  Tailscale Serve 实测只剩四个挂载:`/`、`/dsh`、`/agent`、`/calendar`;裸 `/login`、`/admin`、
  `/api`、`/static` 已撤掉,经 tailnet 访问会落到 DSH 上返回 401。
- 实测(2026-10-12 真机,容器):`/calendar/login` 200、`/calendar/register` 200、
  `/calendar/static/css/app.css` 200;`/calendar`、`/calendar/`、`/calendar.ics` 均
  `404 text/plain`;`/calendar/api/v1/events` 匿名 `401` 且是应用自己的 JSON
  (`{"error": {"code": "unauthorized"}}`),不是 HTML。
- 历史记录:2026-09 时裸路径**没有**挂到本服务(命中 `/` 路由转发到 DSH,与 SisiCalendar 无关);
  2026-10-11 起才挂上,随后在 2026-10-12 收窄为只挂 `/calendar`。
- **部署过程中发现并修复的真实缺陷**:Tailscale Serve 会剥掉挂载前缀。最初按设计文档的命令
  用 `--set-path=/calendar http://127.0.0.1:443` 配置后,`/calendar` 落到后端 `/`(管理首页的
  303 重定向),`/calendar/login` 返回 200(登录页),`/calendar/api/v1/events` 返回 401——
  **管理面暴露给了整个 tailnet**。把目标改为 `http://127.0.0.1:443/calendar` 后,
  后端路径变为 `/calendar` 且其余子路径一律 404,问题消除。
- 由于 Docker NAT 让本机请求与代理请求的来源地址相同(容器内均显示为 `172.19.0.1`),
  应用层无法区分二者,**不要靠客户端地址做管理面隔离**;判定一律走账号与角色。
  当前隔离口径是:对外只有 `/calendar` 一个前缀,该前缀下的管理页与管理员 API 一律要求
  登录 + 管理员角色(成员访问 `/calendar/admin/members`、`/calendar/admin/settings`、
  `/calendar/admin/sync` 与相关 API 仍 403);《部署与运维》第 3 节已同步命令、路径映射表与检查清单。

### 21.(2026-10-08 新增)本轮缺陷修复:邮件附件的「今天」按应用默认时区计算

| 验收标准 | 对应测试 | 结果 |
|---|---|---|
| `build_range` 的缺省起点是**应用默认时区的当地今天零点**;在 UTC+10 这类时区里,当地刚过午夜时**昨天的全天事件不会**重新进入邮件附件 | `tests/test_mail.py::test_attachment_keeps_all_day_events_of_today` | 通过 |

- **缺陷**:`app/events.py::build_range` 的缺省起点原先用 **UTC 的「今天」** 去套当地零点。
  `DEFAULT_TIMEZONE=Australia/Brisbane`(UTC+10)时,当地刚过午夜而 UTC 还停在前一天,
  于是「今天」被算成了前一天,**昨天的全天事件**会重新出现在邮件附件里。
- **修复**:先 `utc_to_local(utcnow(), tz)` 取当地日期,再换算成当地零点;
  文档串与注释也写明了这条口径。
- 回归测试:`tests/test_mail.py::test_attachment_keeps_all_day_events_of_today`。
  该用例本就以 `utc_to_local(utcnow(), mail_settings.default_timezone).date()` 定义「今天」,
  因此同时守住了「全天事件按当地日期比较」与这次的时区边界缺陷。

## 迭代记录:提醒(VALARM)与备注链接(URL)

### 需求

「更加完善 iPhone 日历的基础功能,包括提醒 / 备注」。核对现状:

- **备注**已经有对应字段(`description`),iOS 会把它显示在事件详情的「备注」里;
  缺的是 iPhone 日历同样有的 **URL 链接**字段;
- **提醒完全缺失**:导出里没有任何 `VALARM`,所以订阅端/导入端都拿不到服务端配置的提醒。

### 关键设计决定(以及为什么)

| 决定 | 理由 |
|---|---|
| 提醒用**相对时长**(`TRIGGER:-PT15M`),不用绝对时间 | 重复事件与跨时区/夏令时事件由订阅端按各自实例的开始时间计算,不必逐实例生成提醒,也不会因夏令时换算产生偏差 |
| 全天事件的基准是开始日 `00:00` | 与 iCloud 语义一致:`1440` = 前一天零点,而不是「前一天的同一时刻」(全天事件压根没有时刻) |
| 存储是**分钟数 JSON 列表**,不是把偏移量塞进 `rrule` 之类的位置 | 一条事件多条提醒是常态;JSON 列表可读、可增量扩展,且与既有 `app_settings` 的覆盖项风格一致 |
| 入库前**去重并按从大到小排序** | 导出器靠内容哈希判断是否需要新版本(不变量 3)。顺序若随输入漂移,同一组提醒会算出不同哈希,导致没有改动的保存也向所有同步人员重发整份日历 |
| 不提交 `reminders` = 保留原值,提交 `[]` = 清空 | 与 `title`/`location` 等字段的 PATCH 语义一致;也让「只改标题」的调用不会意外抹掉提醒 |
| 非法值**报错**(422)而不是静默忽略 | 沿用仓库既有约定:「拼错参数应当失败,不应被接口猜中」 |
| 新增列全部可空,无提醒/无链接的事件导出**逐字节不变** | 升级本身不得触发重发:旧事件没有 `reminders`/`url`,导出结果与升级前相同 |
| 不做「默认提醒」设置项 | 需要再开:先看真实使用中是否真的需要统一默认值,避免为一个未验证的需求动 `app_settings` 与导出默认值 |

## 迭代记录:邮件附件只含尚未结束的日程 + 正文按提交时区(2026-10-06)

### 需求

1. **邮件不再发过去的事件**:订阅日历显示正确,但邮件(尤其是打开附件时)带着一堆历史日程,
   通知价值低。用户选择「只改附件,附件只附未来的全量日程」。
2. **邮件正文的时间按提交时区表述**:快捷指令带 `+11:00` 提交时,正文却按事件的参照时区
   (常驻时区)显示成另一个钟点,读起来像"错了"。

### 关键设计决定(以及为什么)

| 决定 | 理由 |
|---|---|
| 过滤**只发生在邮件专用快照**上,发布文件与版本快照保持完整 | 「未来」是相对挂钟时间的概念。若让发布文件过滤,导出内容就依赖导出时刻,直接违反不变量 3(见 `test_content_is_deterministic_across_wall_clock`):没有改动的保存也会因某条日程刚好过期而改变哈希、递增版本、向所有人重发;订阅端还会随时间"掉事件"、手机丢掉历史 |
| 新增第二个快照文件 `calendar-v{N}-upcoming.ics`,不建数据库列 | 路径由版本号推导即可(`mail_snapshot_path_for`),任务记录里既有的 `snapshot_path`/`attachment_hash` 原样复用;不变量 6(附件取自该任务的不可变快照、重试不冒充新版)完全保持不变 |
| 快照缺失时**回退到版本快照**(附完整日历) | 升级前创建的版本没有这个文件;宁可多发历史日程,也不能让任务因为找不到文件而报"快照缺失"而失败 |
| 判据复用 `expand_occurrences`,而不是自己比大小 | 一次性事件按区间重合、重复事件按展开结果,三种情况自动正确:未来事件、**正在进行**的事件(起点在过去)、**起点很早但仍在重复**的序列。自己写 `end_at < now` 会把仍在重复的序列整条丢掉 |
| 分界是**此刻**(`utcnow()`),不是「今天 00:00」 | 用户要的是「不再发送过去事件」,那么**当天上午刚开完的会**也不该跟着下次邮件发出去;实现上只把窗口的 `start_utc` 换成此刻,`start_date` 不动,于是全天事件仍按当地日期判断(「今天」的全天事件照旧保留)。附件是「每个版本只写一次」的产物,所以分界随钟表移动不会让同一版本前后不一致 |
| 邮件正文按**提交文本里的偏移量**表述,标签写 `UTC+11:00` | 邮件是纯文本、收件端不做换算,只有按提交者的钟点写才可读;事件的 `timezone` 保持不变,订阅日历与 ICS 仍是"按收件人所在地显示"。标签用固定偏移而不是猜一个 IANA 名,避免在 `timezone` 与偏移量不一致时写出错误的时区名 |
| 不能用 `a or b` 选偏移量 | `timedelta(0)`(提交 `Z`)是假值,会被误判成"没提交偏移量";实现里用显式的 `is None` 判断,并有测试守着 |
| 网页表单不加偏移量 | 表单用的是 `datetime-local`,本来就没有时区信息;从 `/admin` 建的事件仍按事件时区表述。行为差异已写进《部署与运维》 |

## 3.4 迭代记录:家庭多人共享日历(2026-10-08)

### 需求

从单用户私有日程服务演进为**家庭多人共享日历**:3–5 个账号,每人一条**只有本人可见**的
私人日历,外加一条全家共享的日历;每人在自己 iPhone 上订阅自己的范围,邮件也只按各自范围发送。

### 已实现(全部通过测试,非计划)

| 层 | 内容 |
|---|---|
| 数据模型 | 迁移 `migrations/versions/0005_family_accounts.py` **只做结构变更**:新建 `users` / `calendars` / `calendar_members` / `invite_codes` / `feed_tokens`;`events` 加 `calendar_id`(FK `calendars.id`,`ON DELETE SET NULL`)与 `created_by_user_id`;`sync_recipients` 加 `user_id`;`agent_tokens` 加 `user_id` / `calendar_id`(详见《部署与运维》9.1) |

| 管理员职责 | 成员(停用 / 启用、重置口令、改角色、删除)、邀请码、应用设置、同步与手动发信、外部收件人;不能停用 / 删除自己,也不能删掉最后一个管理员(409) |

### 关键设计决定(以及为什么)

| 决定 | 理由 |
|---|---|
| 隐私判定下沉到一个 `CalendarAccess`(可见 id 集合 + `can_view` / `can_write`) | 读接口漏一处过滤就是隐私事故;集中判定后,**越界事件在列表里根本不出现**、按 id 读 404,不靠每个接口各自小心 |
| 数据回填放在启动引导 `ensure_family_setup`,结构变更放在 Alembic | 回填要读环境里的管理员凭据,迁移里读不到;分开之后引导可重复执行且无副作用 |
| 版本号与内容哈希仍由**全库并集**决定,不改成按目标分别计数 | 保持不变量 3(导出内容只取决于数据库状态)。`export/calendar.ics` 退居**内部一致性产物**,对外只暴露 `export/feeds/<key>.ics`,但任何成员的改动仍会推进全局 `export_version` |
| 旧地址绑定**首位管理员**而不是全库并集 | 升级后既有 iPhone 订阅不能突然多出别人的私人日程;绑定首位管理员正好等于「升级前他看到的东西」 |
| 邮件按收件人取**各自目标**的快照 | 附件范围随收件人不同,不能再共用一份快照;任务记录里既有的 `snapshot_path` / `attachment_hash` 原样复用,不变量 6 不变 |
| 邀请码与订阅令牌都只存 `sha256` | 与远程接入令牌同级处理:数据库或备份泄漏不暴露凭据,明文只在创建那一次显示 |
| 账号邮箱是账号收件人的**唯一来源**,外部收件人接口拒绝账号行(409) | 否则同一个人的收件范围会随改动路径不同而漂移;一个来源才能保证「账号收件人 = 自己可见范围」这条口径 |

2. **旧的无令牌订阅地址彻底取消**:`/calendar` 与 `/calendar.ics` 不再服务任何日历。
3. **每个账号一条固定订阅地址**:服务端派生、永不变更,界面可以随时重新显示。
4. **邮箱验证**:注册必须填邮箱,6 位验证码通过后才能用系统;验证通过后收到一封含**本人固定
   订阅地址**的邮件;改邮箱立刻打回待验证。
5. **邮件正文不再出现并集订阅地址**:账号收件人拿到**自己**那条地址,外部邮箱一条都不给。

### 关键设计决定(以及为什么)

| 决定 | 理由 |
|---|---|
| 前缀**按请求推导**,不写成常量 | 同一个应用要同时服务本机裸路径(`http://localhost:443/admin`)与家庭成员的 `/calendar/...`;写死常量后从裸路径进来的页面会把家人甩到只在本机可达的地址上。`ContextVar` 让模板与重定向都跟着入口走 |
| 绝对地址一律取自 `PUBLIC_BASE_URL` | 邀请链接要能直接复制粘贴给家人、订阅地址要能直接粘进 iPhone;这些地址必须带 `https://<节点>/calendar`,不能靠请求头猜(经代理后 Host 不可靠) |
| 路由挂载路径与后端路径**逐字一致**,不做前缀剥离 | 与本仓库既有的 Tailscale Serve 用法一致(`--set-path=/calendar` 配 `http://127.0.0.1:443/calendar`),少一层"剥前缀"的隐式约定 |
| 订阅路由限定 `/{token}.ics` | 否则 `/calendar/<任意段>` 都会被订阅路由吃掉,前缀下的登录页 / 管理页再也挂不上 |
| 旧无令牌地址回 **404 纯文本**而不是 303 | 订阅端会把 303 的目标当成 HTML 日历存下来;要对机器说机器话。浏览器(明确 `Accept: text/html`)才 303 到管理页 |
| 固定地址由**服务端密钥派生**而不是随机数 | 界面要能长期显示、验证通过后要能邮件告知,而库里仍然只存哈希;代价是轮换 `data/session_secret` 会让所有固定地址与验证码哈希一起失效——这是刻意的取舍,密钥即身份 |
| 固定地址**不给停用 / 撤销**(409) | 它是手机上长期填着的那条,误点停用会让订阅静默失效;想要临时地址另建一条随机令牌(仍可停用 / 撤销) |
| 验证码只存 **HMAC**,不存明文 | 6 位验证码的空间只有 100 万,裸哈希可被穷举;用服务端密钥做 HMAC 后,单独泄漏数据库无法反推 |
| 第 5 次错误直接作废验证码 | 与「最多错 5 次」等价但更干净:作废后必须重新发送,不给暴力尝试留下窗口 |
| **管理员豁免**验证闸门 | 本机救急时不能被自己的邮箱锁在门外;没有邮箱的成员也不挡(升级上来的老账号可能还没填),只在界面提示 |
| 验证通过才建账号收件人 | 邮箱是否真的属于本人,直接决定订阅地址与日历快照发到哪里;`sync_user_recipient()` 只认「有邮箱 **且** 已验证」 |
| 改邮箱立刻打回待验证并重发验证码 | 验证码与邮箱绑定;否则改成别人的地址就能把订阅地址发到任意邮箱 |
| 外部邮箱(含历史邮箱)一条地址都不给 | 账号的固定地址是**个人凭据**;历史邮箱只是替首位管理员收信,给它地址等于把某个账号的订阅入口交出去 |

## 3.8 迭代记录:同步邮箱收敛到外部邮箱 + 只通知「看得见的人」(2026-10-12 第四轮)

真机反馈:**共享日历里日程变动时,范围内的家人收不到同步邮件**,只有「设置」页里那几行
同步邮箱在收信。用户要求:设置里的同步邮箱功能**收敛到外部邮箱**;某成员可见日历变动时,
要把这次变更同步给**范围内用户已认证的邮箱**,并附上「未竟日程」的 ICS 副本。

### 根因

账号收件人虽然由 `users.email` 派生,却是一行**可被设置页删掉/停用的普通记录**:

1. `app/routers/pages.py::remove_recipient` / `toggle_recipient` **没有任何守卫**
   (只有 `/api/v1/sync-recipients` 拦了改名与删除),管理员在设置页就能把成员的账号收件人删掉;
2. 删掉之后**没有任何路径把它补回来**——引导里的 `sync_user_recipient` 虽然每次都跑,
   但结尾 `session.commit()` 只在 `changed` 为真时执行,而账号收件人的修复**不会**置 `changed`。
   真机库里的现场正是:两位成员邮箱都已验证,`sync_recipients` 里只剩一行。

### 需求与实现

| 项 | 实现 |
|---|---|
| 账号收件人 = 派生数据 | 新增 `app/accounts.py::sync_account_recipients(session) -> int`:启用 + 已验证 → 一条**启用**的账号收件人;账号停用 → 该行 `enabled=False`(不删行);返回变化行数供调用方提交。`sync_user_recipient()` 补上「账号启用时把该行恢复成启用」 |
| 三个对齐时机 | 启动引导、**建发信任务之前**(`ensure_delivery_tasks`,不依赖上一次启动是否修好)、设置页与收件人片段渲染前 |

| 设置页收敛到外部邮箱 | `_recipients()` 只返回 `user_id IS NULL` 的行;新增 `_account_recipient_entries()` 渲染只读的「账号邮箱(自动同步)」表;新增 `_guard_external_recipient()`,停用/移除命中账号行返回 **409** |
